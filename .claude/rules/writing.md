# 執筆ルール

> **プロジェクト決定録**: 教材ごとの選択（様式・学習モデル・アークモード・検証モデル等。キーの一覧と意味は `PROGRESS.md` テンプレートの config コメントと /pilot の決定録表を正とする）は `PROGRESS.md` frontmatter の `config` に集約する（単一ソース・fw-sync 不可侵）。本ファイルで「/pilot で選択・設定」とある箇所は config を正とし、skills は実行時にそこを参照する。writing.md 自体は題材非依存の共有ルールとして保つ。
>
> **リファレンス優先**: `config.style` が emoji 以外、または `config.section_model` が weave の教材では、対応するリファレンス（`.claude/skills/write/references/styles/<style>.md` / 同 `section-models/weave.md`）の読み替えが本ファイルの該当箇所より優先する。/write・/review は執筆・検査の前にこれらを読み、サブエージェントにもパスで渡す。

## 1. 文体

### トーン

- **本文**: 落ち着いた敬体で、直接的・説明的に書く。過度に個人的な語りかけ（「率直に言うと」等）や、比喩・修辞で飾るエッセイ調の冗長な語りは避ける
  - 比喩を多用しない。「登る道のり」「地図を広げる」「いま立っている場所」のような言い換えより、事実をそのまま述べる
  - 情緒的な前置き・修辞を避ける（「〜という経験はないでしょうか」「まさにそのために」「安心して読み進めてください」等）。課題や意義は一文で端的に示す
  - 字数は内容の厚み（具体例・コード・図・概念の掘り下げ）で満たす。字数の目安に届かせるための冗長な言い換えや装飾はしない
- **🧠 [人格名]はこう考える**: 実体験ベースの語りをここに集中させる。本文より口語的な表現を許容するが、「率直に言うと」「正直に言うと」等の前置きや読者を試す表現は避け、具体的な失敗談・設計判断の裏話・実務のあるあるで語る。分量は **数文程度** に抑える（具体的な経験ひとつと、そこからの学びで十分。長い物語にしない） <!-- 確定値: PROGRESS.md config.persona -->
  - 頻度は `config.persona_frequency` に従う（毎 Section（既定） / 効果的な Section のみ）。いずれでも同型の語り（似た場面・似た教訓）を繰り返さない

### AI 臭の抑制（頻出 NG パターン）

生成時に混入しやすいパターン。表層（記号・強調の書式等）は `scripts/lint_curriculum.py` と textlint が機械検出するため、ここには文章の書き方として効く上位のみを載せる。詳細な観点と 🧠 コラム専用基準は `.claude/skills/review/references/ai-slop-curriculum.md` を参照。

- ハイプ表現（「革命的」「劇的に」「完全に解決」「究極の」）を使わない。効果は事実と数値で述べる
- 「A ではなく B」の対比構文は 1 Section 2回まで。多くは「B です」と直接書ける
- 3項目並列を機械的に作らない。本当に3つか疑い、2つ・4つに崩せるなら崩す
- 冗長表現を避ける: 「〜することができます」→「〜できます」、「〜を行います」→「〜します」
- 比較・選択を示す場面では両論併記で終えず、本教材としての推奨と理由を明示する
- 段落末を同じ型（「〜が重要です」等）で繰り返し締めない

### 用語・表記

- 敬体（です・ます調）で統一。読者を指す語は「あなた」「学習者」を用い、特定の制度名・組織名（受講区分・所属組織名など）は本文で使わない
<!-- 確定値: PROGRESS.md config.excluded_terms。運営側の背景・事情、固有名、評価・採点に関する表現などを本文から除外する方針があれば、言い換え先とともに定義する -->
- ダッシュ記号（`——`、`—`、`–`）は使わない
- 教材トピックの用語は参考資料の表記に従う。範囲外の内容は WebSearch / WebFetch で裏付ける
- 時間経過で変わる情報は最新情報を取得し「○○時点」と日付を明記
- 教材が前提とするバージョンと、読者が現場で遭遇しうるバージョンに差がある場合は、本文は前提バージョンで書き、差分は 💡 / 📝 の短いコラムで補足する（本文を散らかさない）
- 外部ソースを参照する場合は出典を明記する
- 出典リンクは Section 内初出の1回だけ張り、2回目以降は素のテキストにする。「公式ドキュメント」と書くときはどのページかを補う。引用文はページに実在することを確認してからリンクし、URL の無い出典（書籍等）はリンクにしない
- `**太字**` は語句・キーフレーズに限定する。文全体を太字にしない。💡 / 🔑 / 📝 プレフィックス付きの行でも同様（❌ `💡 **○○は△△です。**` → ✅ `💡 ○○は **△△** です。`）
- Markdown の `**text**` は閉じ `**` 直後にスペースなしで日本語が続くと適用されない。`**○○** の場合` のようにスペースを入れる。全角括弧 `（` も同様: `**○○**（補足）` → `**○○** （補足）`

| 表記 | 備考 |
|---|---|
| セクション | 教材本文ではカタカナ表記。内部ドキュメントでは英語 |

### 表現様式（4様式・config.style）

<!-- 確定値: PROGRESS.md config.style（/pilot が記録）。選択肢: emoji（既定・GitHub 直読み向け） / plain / admonition / zenn。
     骨格（枠見出し・ブロック構成・順序）は全様式で共通とし、記号・記法だけを差し替える。
     emoji 以外を選んだ場合: 様式リファレンスの読み替えが本ファイルより優先し、lint・hook・CI・/review は config.style に自動追随する -->

様式は公開方式に合わせて選ぶ。emoji 以外の詳細規則（対応表・コード記法・折りたたみ・画像キャプション・lint 挙動）は様式リファレンスが正:

| style | 想定公開先 | 概要 | 詳細規則 |
|---|---|---|---|
| `emoji`（既定） | GitHub 直読み | 11絵文字の機能マーカー（下表） | 本ファイル |
| `plain` | 汎用 Markdown・LMS 貼り付け・生成 AI 特有の装飾感を避けたい教材 | 絵文字ゼロ。テキスト見出しと太字ラベル | `.claude/skills/write/references/styles/plain.md` |
| `admonition` | MkDocs Material（/github-pages） | `!!!` 記法のコールアウト | 同 `styles/admonition.md` |
| `zenn` | Zenn 互換レンダラ（zenn-markdown-html 採用 LMS 等） | `:::message` 等の Zenn 記法 | 同 `styles/zenn.md` |

**全様式共通の不変条件**: ①枠見出し（テンプレート固定部）以外の本文見出しに絵文字・装飾を付けない ②コールアウトの語彙を増やさない（種類は各様式の対応表が全て） ③同種コールアウトを連続配置しない・1 Section 3〜4個まで ④絵文字をビュレット代用・本文の装飾に使わない（emoji 様式でも絵文字は下表の機能マーカー限定）

**絵文字様式（既定）**:

| 絵文字 | 用途 |
|---|---|
| 🎯 | 学習目標（Section 冒頭） |
| ✨ | まとめ（Section 末尾） |
| 💡 | TIP・補足 |
| ⚠️ | 注意事項・よくあるエラー |
| 📝 | ノート・定義・補足説明 |
| 🔑 | 重要概念・キーポイント |
| 🏃 | ハンズオン手順・実践（weave では役割行 `🏃 **入力**:` / `🏃 **実行**:` にも使う） |
| 🧠 | 経験者の視点・思考プロセス |
| 📌 | 操作前の確認事項 |
| ✅ | 完成チェックリスト（ハンズオン・混合） |
| 📖 | この Chapter の進め方（2層以上の場合）・読む例の役割行 `📖 **読む例**:`（weave） |

## 2. 構造

### Section の種類と学習モデル

<!-- 確定値: PROGRESS.md config.section_model（/define の HOW で確定・G2 の構造決定。変更は /revise 扱い） -->

Section の種類は3つ。**どの種類を既定にし、どう混ぜるか**は教材の学習モデル `config.section_model` で切り替える。

| 種類 | 内容 |
|---|---|
| **概念** | 意義・仕組み・使い方を解説（コードは読む例）。末尾に任意の小実践「やってみよう」を置ける |
| **ハンズオン** | 既習の複数機能を束ねて成果物を作る統合実践。冒頭に概念 Section への逆リンク |
| **混合** | 説明と操作が不可分。構成は2形: **二段構成**（前半で概念解説 → 後半 `## 🏃 実践:`）/ **織り込み構成**（本文の `##` 見出しの合間に説明と `### 🏃 Step N` を交互に流す） |

| section_model | 向く教材 | 種類の使い分け | 混合の既定形 | ペーシング検査（/outline） |
|---|---|---|---|---|
| `separate`（分離型・既定） | 読解中心（概念を深く読み、実践を集約する） | 下の判定表 | 二段 | 実践接点（やってみよう・混合・ハンズオン）の無い概念 Section を3連続以上並べない（純理論中心の Chapter は種類方針に理由を明記して例外可） |
| `weave`（織り込み型） | タイピング中心（短い説明→打つ→確認のループが本文の主役。完全初心者向けチュートリアル等） | **既定は混合（織り込み）**。概念は Chapter 0〜1 目安・ハンズオンは章末/部末。判定・骨格・執筆規範・役割行は `.claude/skills/write/references/section-models/weave.md` が正 | 織り込み | 逆向き: 各 Chapter に非タイピング接点（概念 Section または想起まとめ指定節）を最低1つ |

**使い分けの判定**（separate の場合。Section の主目的で決める）:

| 判定 | 種類 |
|---|---|
| 分かるが目的。手を動かす価値が薄い | 概念 |
| 分かるが目的。その節の機能を 5〜15 分の自己完結な試行で定着させられる | 概念＋やってみよう |
| 作りながらでないと説明が冗長になる（説明と操作が不可分） | 混合 |
| 既習の複数機能を組み合わせて成果物を作る | ハンズオン |

混合の構成形を Section 単位で既定から変える場合（例: weave 教材の環境構築節を二段にする）は、OUTLINE の種類フィールドに「混合（二段）/ 混合（織り込み）」と注記する（無印は section_model の既定）。判定基準: 概念導入が3段落を超える・実践が分割不能な一塊なら二段、それ以外は既定。

### 見出しの設計

**Why → What → How**（抽象→具体）の流れで組む。枠見出し（🎯 ✨ 📌 🏃 ✅ 等のテンプレート固定部）以外の本文見出しには絵文字を付けない。

**見出し規律（5項目）**: Section 内の `##` 見出しは、次を守って形と粒度を揃える（バラバラだと読者が各見出しの役割をつかめず「構成が分からない」となる）。

1. **形を揃える**: 名詞句／動詞句で統一する。断定文（「〇〇が…する」）・対応マッピング文（「A は X、B は Y」）は見出しに使わない。疑問形の例外は「〇〇とは（何か）」と、モード2の Why 定型「なぜ〇〇を使うのか」の2つだけ
2. **1見出し1役割**: 各見出しは「定義（What）／仕組み（How works）／使い方・運用（How use）／効果（benefit）」のいずれか1つを担う。同じ役割を 1 Section 内で2回置かない（重複したら統合する）
3. **アークを通す**: 下記のモードに沿って Why → What → How の順に並べる
4. **括弧で具体を添える**: 見出しの括弧に具体語（コマンド・用語・対象）を入れる（例: `努力レベルを切り替える（/effort）`）
5. **粒度を均す**: 大きいトピックに1見出し。小トピックに2見出し・大トピックに1見出しのような偏りを作らない

**アークの2モード**: Why をどこが担うかで2通り。**Why は1か所だけ** に置く。<!-- 確定値: PROGRESS.md config.arc_mode -->

- **モード2（概要駆動・既定）**: 先頭の概要のあとに、Why と What を定型見出しで立てる。

    ```text
    ## 概要                  ← Section の主題と流れを1〜2文
    ## なぜ〇〇を使うのか      ← Why（課題・動機。🧠 コラムはこの配下）
    ## 〇〇とは何か            ← What（定義）
    ## [仕組み／使い方が並ぶ]   ← How（括弧に具体語）
    ```

- **モード1（導入駆動）**: 課題・痛みから入る `## 導入: 〇〇` が Why を担う。「なぜ〇〇を使うのか」という独立見出しは置かない（導入と重複するため）。

    ```text
    ## 導入: [課題・痛み]    ← Why（🧠 コラムはこの配下）
    ## 〇〇とは（定義）       ← What
    ## [仕組み／構成]         ← How works
    ## [使い方／運用]         ← How use
    ```

### テンプレート

全 Section 共通の骨格に、種類ごとの差分を組み合わせる。Why ブロックは config.arc_mode（/pilot が記録）で選んだアークモードの形を使う（下記はモード2（既定）の骨格）。**weave の混合（織り込み構成）だけは専用の開始アークを使う**（arc_mode は N/A。骨格は `section-models/weave.md` が正。概念・ハンズオンは weave でも本テンプレートに従う）。

```markdown
# [セクション番号] セクションタイトル

<!-- 前提がある場合: 📝 **前提知識** 行を挿入 -->
<!-- 概念（グループ先頭）の場合: グループ全体像を挿入 -->
<!-- ハンズオンの場合: 📝 **このハンズオンで使う機能** 行を挿入 -->

## 🎯 このセクションで学ぶこと

- 学習目標1
- 学習目標2

---

## 概要

[Section の主題と流れを1〜2文で示す]

## なぜ〇〇を使うのか

[課題・動機。これがないと何が困るかを端的に]

### 🧠 [人格名]はこう考える

> [実務の経験に基づいて自由に語る]

---

<!-- 本文: 「〇〇とは何か」（What）から How へ。種類ごとに異なる（「種類ごとの差分」を参照） -->

---

<!-- 概念で「やってみよう」を置く場合: ここに ## 🏃 やってみよう: [具体タイトル]（「種類ごとの差分」を参照） -->

## ✨ まとめ

- ポイント1
- ポイント2

---

次のセクションでは、[次の内容への接続]。
```

モード1（導入駆動）を選んだ場合は、「概要」〜「なぜ〇〇を使うのか」を `## 導入: [課題・痛みから入る見出し]`（直下に 🧠）へ差し替え、🎯 ブロックの直後に [1文で Section の流れを示す] を置く。

**次セクションへの接続**:
- プレーンテキストで記述する（Markdown リンクやカギ括弧は使わない）
- **次セクションへの接続文** は、OUTLINE.md の次セクションのゴールに含まれるキーワードを漏れなく含める
- **Chapter 最終セクション**: Chapter の学びの振り返り + 次の Chapter への橋渡し
- **Part 最終セクション**: 上記に加え、Part 全体の振り返り + 次の Part への橋渡し
- **教材全体の最終セクション**: 教材全体の締め括り文を記述する（学んだことの振り返り + 次のステップへの示唆）

### 種類ごとの差分

**概念**:

- 本文は `## 見出し` で構成する
- 2層以上の場合、親グループの最初の Section のみ、タイトル直後にグループ全体像を含める。種類が混合でもグループ先頭であれば同様に含める。グループ全体像は `##` 見出しを使わず、タイトル直後に直接記述する。構成: ① 概要文（1-2文）② セクション一覧テーブル（セクション / テーマ / 種類）③ `📖 **この Chapter の進め方**: [学習の流れ]`
- 末尾（まとめの直前）に任意で `## 🏃 やってみよう: [具体タイトル]` を置ける:
  - **置く基準**: その節で学んだ機能を単独 5〜15 分で試せ、観察できる達成状態で確認できる場合のみ。薄い確認しか作れない節・直後のハンズオンが同じ機能を同じ題材で扱う節には置かない
  - **自己完結**: 成果物・環境変更を後続 Section で当てにしない。環境を変える操作（設定・接続等）は節末で元に戻す
  - **書式**: 手順は太字番号（`**1. 〇〇**`）で書き、ハンズオンの `### 🏃 Step N` と峻別する。固定コマンドは bash、貼り付け文は text ブロック。後片付け → ✅ の確認（観察できる達成状態）で締める
  - **難易度**: Part 内で「再現する → 1点だけ変える → 目標だけ提示」と徐々に足場を外してよい
  - **執筆タイミング**: <!-- 確定値: PROGRESS.md config.tryit_timing。A（Part単位2パス・推奨） / B（同一パス）。2パス運用の手順詳細は /write スキルを正とする。weave では N/A（section-models/weave.md） -->

**ハンズオン**:

- タイトル直後に `📝 **このハンズオンで使う機能**: [機能名]（[セクション名] で学習）` を挿入
- 導入の後に `## 📌 [作業名]前の確認`（チェックリスト形式）を挿入
- 本文は `## 🏃 実践: [タイトル]` の中に `### 🏃 Step N: [タイトル]` の連番で構成する
- 本文の後、まとめの前に `## ✅ 完成チェックリスト` を挿入
- 長いコードは `<details>` で折りたたむ

**混合**:

構成は2形（既定は section_model に従う。Section 単位の上書きは OUTLINE の種類注記）:

- **二段構成**: 本文の前半は `## 見出し`（概念解説）、後半は `## 🏃 実践: [タイトル]` の中に `### 🏃 Step N: [タイトル]` の連番で構成する
- **織り込み構成**: `## 🏃 実践:` コンテナは置かず、本文の `##` 見出し（トピック）の配下に説明ブロックと `### 🏃 Step N: [サブゴール]` を交互に流す。Step 番号は Section 内の通し連番（見出しをまたいでもリセットしない）。開始アーク・境界規則・役割行・執筆規範は `section-models/weave.md` が正
- どちらの形でも、本文の後・まとめの前に `## ✅ 完成チェックリスト` を挿入し、長いコードは折りたたむ（記法は様式に従う）

**エラーフォーマットの使い分け**:
- エラーメッセージ（コードブロック）を伴う場合 → blockquote 形式（下記テンプレート）
- エラーメッセージなしの一般的な注意 → `⚠️ **注意**: ...` でインラインに記述

> ⚠️ **よくあるエラー**: [概要]
>
> ```

## 3. コンテンツ

### コードの見せ方

- コードを含む場合、コードブロック上部にファイルパスをコメントで明示する。コメント構文は言語タグに合わせる:
  - `java` / `typescript` / `javascript` / `php`: `// filepath`
  - `tsx` / `jsx`: `{/* filepath */}`
  - `yaml` / `properties` / `dockerfile` / `bash`: `# filepath`
  - `css`: `/* filepath */`
  - `html` / `xml`: `<!-- filepath -->`
  - `sql`: `-- filepath`
  - `<?php` で始まる PHP ファイルなど、先頭に固定行があるファイルは、パスのコメントをその固定行の **次の行** に置く（固定行より前に置くと、そのまま貼り付けたときにコードの外側のテキストとなり壊れるため）
- コードブロックには必ず言語を指定する。非コードコンテンツ（ディレクトリツリー、コマンド出力等）には `text` を使用する
- diff 表示は使わない（テキストで説明し変更後のコードを示す。zenn 様式のみ、読む用の変更説明に限り diff 記法可: `styles/zenn.md`）
- **参考資料のコードを引用する場合は正確性を最優先する**。コードを簡略化して掲載する場合は、コードブロックの直前に「以下は主要部分の抜粋です」と明記し、省略した重要な処理を本文で補足する。ファイルパス・変数名・設定値は実ファイルと完全に一致させる
- 図（処理フロー・リレーション・ER 図等）を Mermaid で描く場合、コードブロックの言語タグは `mermaid`

### 例示コードと実行コードの区別（位置ルール）

「読む例なのか、実際に打つのか」は記述位置で一意に決める。学習者が覚えるルールを1つにする: **打つのは実践見出しの配下だけ**。

- **実践見出し** = emoji 様式では 🏃 見出し（`## 🏃 実践: タイトル` / `### 🏃 Step N: タイトル` / `## 🏃 やってみよう: タイトル`）、plain / admonition / zenn 様式ではテキスト形（`## 実践:` / `### Step N:` / `## やってみよう:`）。**正規形（半角コロン・見出しレベル）の単一ソースは `scripts/lint_curriculum.py` の PRACTICE_* 定数**で、正規形に合わない見出し（全角コロン・コロン欠落・レベル違い等）は lint が 🔴 で検出する（配下のコードが「読む例」扱いに落ちて検証されなくなるため）。別語への言い換え（「動かしてみる」等）は機械検出できないため使わない
- 学習者が実行するコード・コマンドは実践見出しの配下にのみ置く。それ以外の本文コードブロックはすべて「読んで理解する例」であり、実行を促す文言（「実行してください」等）を伴わせない
- **weave（織り込み型）の教材ではさらに役割行で二重に示す**: 打つブロックの直前に `🏃 **入力**:`（対象パスと操作種別）/ `🏃 **実行**:`（実行場所）、実践見出し外の読む例には `📖 **読む例**:` を置く（書式と検査は `section-models/weave.md`）
- **実行用ブロック**: 1コマンド1ブロック。出力やプロンプト記号（`$`）を混ぜない。実行場所（カレントディレクトリ）を明示する（コピペ保証の対象）
- **読む用の実行例**: 出力込み・`$` 付き可。言語タグは `text` にして、観賞用であることを書式でも示す
- 実行ごと・環境ごとに変わる出力（生成 ID・タイムスタンプ・AI の出力等）は、直前に「出力例（環境により異なります）」と明記し、確認は観察できる達成状態で書く

### 解説の深さ

- OUTLINE.md に前提（`前提:` フィールド）が記載されている場合、🎯 の前に `📝 **前提知識**: このセクションは○○の内容を前提としています。` と明記する
- 前提知識（概念）は概念の再入門を省略する。ただし教材トピックでの具体的な実現（記法・作法・差異）は省略せず解説する。既習との差異・組み合わせ時の注意点は特に丁寧に
- トピック固有の概念は初出時に丁寧に解説し、2回目以降は初出 Section への参照
- 同じ概念を別の箇所で繰り返さない
- Why ブロック（モード2: 「なぜ〇〇を使うのか」 / モード1: 導入）は「これがないと何が困るか」（課題）から入る
- 処理の流れ・サイクル・リレーション・ER 図は図で視覚化する <!-- 確定値: PROGRESS.md config.diagram_format（ascii | mermaid）。Mermaid を選ぶと MkDocs Material / GitHub Pages で描画される -->
- 未説明の用語をツリーやリストに含める場合は、簡潔なコメントか後続セクションへの参照を付ける
- つまずきポイントを先回りする（⚠️ で説明）
- 先の Section で扱う内容は「今は概要だけ把握すれば十分です」と明記する
- **概念 Section にコマンドやコードを載せる場合**、それが「読んで理解するための例であり、ここで手を動かす必要はない」ことを学習者に明示する。🎯 ブロックの直後に 💡 で一言添え、文面はやってみようの有無で分岐する（あり: 「このセクションのコード・コマンドは仕組みを理解するための例です。実際に試すのは末尾のやってみようです（本格的な実践は○○）」 / なし: 「…実際に動かす（書く）のは○○（該当ハンズオン / 総合ハンズオン）です」）。混合・ハンズオン Section は実際に手を動かすため、この断りは不要
- 画像は2系統に分けて扱う。**概念図**（メンタルモデルの可視化）は `/illustrate` の担当: 使う場合は執筆段階では挿入せず、挿入位置も `/illustrate` が計画するため TODO プレースホルダーも置かない（密度方針は config.illustrate）。**画面キャプチャ**（実画面のスクリーンショット）は 📸 撮影指示コメントの担当: /write が執筆時に挿入位置へ `<!-- 📸 capture: <対象> / <前提状態・再現手順> / <静止画|gif> -->` を1行で埋め、`/capture` が一括撮影・挿入する（コメントは撮影後も再撮影レシピとして残り `<!-- captured: -->` スタンプが付く。撮影環境は config.capture）。どちらも使わない場合のみ `<!-- TODO: 画像追加 - ○○の画面 -->` でプレースホルダーを残す（TODO コメントの画面名は実際の表示と一致させる。例: 自動ログインされる画面に「ログイン画面」と書かない）
- **画面キャプチャの密度**: 置くのは ①初見で見つけにくい UI 操作 ②紛らわしい選択肢の分岐 ③Step・✅ の結果確認（期待する画面状態の証拠） ④Section 冒頭の完成イメージ（weave のみ・1節1枚まで） の4類型に絞る。コード・ターミナル出力はスクショにせずコードブロックで示す。クリックごとの全画面掲載はしない。alt は画像の内容を説明する日本語で必ず書く（手順文と同じ内容の繰り返しはしない）
- Section あたりの目安文字数: <!-- 確定値: PROGRESS.md config.char_target（例: 4,000 文字程度） -->（必須の下限ではなく、あくまで目安。概念 Section は Why → What → How を丁寧に書くと自然にこの程度を超えることが多い。内容が過不足なく簡潔にまとまっていれば目安を下回ってよい。字数を満たすための加筆はせず、冗長を避けて概念理解を優先する）

### 実践の再現性（実践見出しを含むすべての Section）

対象は実践（🏃）・章末/総合ハンズオン・混合 Section の実践パート・やってみようのすべて。大原則は1つ: **学習者が各コマンド・コードを上から順に、そのままターミナル / エディタにコピペして進めれば、記載どおりの結果になる**ことを、実際の動作から確認する。複数 Section をまたいで 1 つの成果物を積み上げるハンズオン（総合ハンズオン等）では、各 Section の境界でビルド / 実行が通ることまで保証する。

**状態の契約（📌 と ✅）**

- **前提状態を明示する**: 各ステップの実行前に必要な状態（コンテナ起動済み、特定ブランチにいる等）を `📌` チェックリストで示す
- **✅ と 📌 は状態契約**: ✅ 完成チェックリストは観察できる達成状態（「○○すると△△が表示される」等）で書き、次 Section の 📌 が前提とする状態と一致させる（N の ✅ が宣言していない状態を N+1 の 📌 が前提にしない）
- **状態の受け渡しはハンズオン / 混合のみ**: 後続 Section が前提にできる成果物・状態を作れるのはハンズオン・混合だけ。概念 Section（やってみよう含む）は状態中立とし、後続はその成果物を前提にしない
- **副作用のクリーンアップ**: 実践で作成したブランチ・コミット・ファイル変更は、セクション末尾で元に戻す手順を必ず含める。特に Git 操作（`git checkout`, `git restore`, `git reset` 等）は、ステージ状態・ブランチ状態を正確に追跡する
- **実行検証のスタンプ**: 手順を実機検証した Section には冒頭に `<!-- verified: YYYY-MM-DD 環境 -->` を残す。コードブロックを変更したら再検証してスタンプを更新し、検証していない場合はスタンプを置かない

**コードはコピペでビルド / 実行が通る形にする**

- 定型コード（getter / setter 等）を「エディタで生成」に委ねず、後続 Section がそれを参照するなら省略せず全掲載する。揃っていないとビルドが通らない（生成方法は補足に留める）
- **前方参照しない**: 各 Step のコードは、その時点で既に定義済みのものだけを参照する。動作確認より後の Step で追加する処理を先に呼ばない
- 「既存ファイルに追加 / 置換」する Step では、**どのファイルのどこへ** 入れるか（先頭・特定ブロック内・全体差し替え等）を明示する
- **完全コピペの担保**: 学習者が新規作成する、または構造的に書き換えるファイル（設定ファイル・モデル・コントローラ等）は、**ファイル全体をそのまま貼れる形** で示す（生成直後のファイルをまるごと置き換える指示にする）。逆に、大きな既存ファイルのごく一部だけを変える場合（テンプレートの 1 ブロック、`// TODO` のような一意なアンカー行の置換など）は、**どこを** 置き換えるかを明示したうえで変更箇所だけを示す（無関係な既存コードは再掲しない）。長いファイル全体を見せるときは折りたたむ（記法は様式に従う。emoji 様式は `<details>`）

**足場（環境・配置）の手順を省略しない**

- ディレクトリ作成・展開・`cd`・エディタで開く操作・ファイルの配置先を省略しない。各コマンドの実行場所の明示は「例示コードと実行コードの区別」の実行用ブロック規則に従う
- 新規ファイルを作る Step では、**ファイル作成を明示的なコマンドで示す**。`mkdir -p`（ディレクトリ）と `touch`（ファイル）で作成してから内容を提示し、コードブロックのファイルパスコメントだけで「作成済み」と暗黙に扱わない。既存ファイルへの追記・編集と新規作成を明確に区別する
- OS 差を補足する（コマンド名・パス区切り等）。初出で一度示し「以降も同様」と添える。admonition 様式（MkDocs）の教材では、まとまった操作ブロックの OS 差はコンテンツタブ（`=== "macOS"` / `=== "Windows"`）で書き分ける: ラベル表記は固定・並びは macOS → Windows・短い差はタブ化せずインライン併記・中身は4スペース字下げ（`content.tabs.link` でサイト全体のタブ選択が連動する）

**動作確認は実際の挙動と一致させる**

- レスポンス本文がない成功（HTTP 201 等）はステータスを可視化する手段（`curl -i` 等）を示す
- 出力例（ソート結果・整形結果・ログ）は、掲載したコードを実行したときの **実際の結果** と一致させる。憶測で書かない
- 想定どおり起きる中間状態（認証必須パスで 401 になる等）は「正常です」と明記し、非同期処理は結果の確認方法まで示す
- **REPL（対話型シェル: Tinker / IRB / node / python 等）で動作確認させる場合**: ① メソッドチェーンなど 1 つの文は **1 行で書く**（複数行に分けて貼ると行ごとに評価され、行頭が演算子（`->` 等）で始まる行が構文エラーになる REPL がある。クロージャは 1 行に収める）。② マルチバイト文字（日本語等）は REPL の表示でバイト列（`<E4><BB><95>` など）に化けることがあるため、サンドボックスの実験データは **英語のラベル** にして出力を読みやすく保ち、出力例も実際の表示に合わせる

**フレームワークの挙動は裏取りしてから断定する**

- 「このコードで動く」「この設定で解決する」が成否を分ける箇所（依存名・読み込まれる設定・アノテーションや記法の要否・バージョン専用機能等）は、公式ドキュメント等で **対象バージョンでの挙動** を確認してから書く

**コードを書かない設計 Section の表現**

- 設計だけで成果物（ファイル）が生まれない Section では、「完成チェックリスト」「成果物が揃っている」といった表現を避け、「設計を説明できる / 決められた」など **理解・意思決定** として書く。冒頭の `📝` も「使う機能」ではなく「活かす概念」等、実態に合わせる

### ハンズオンの検証モデル（確定値: PROGRESS.md config.verification_model）
