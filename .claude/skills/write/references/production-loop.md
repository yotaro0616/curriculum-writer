# 量産ループ（複数 Section の一括執筆プロトコル）

`/write` が複数 Section を含むスコープ（Chapter・Part・`全て`）を扱うときの実行プロトコル。新規の量産にも、既存 Section の一括更新・ブラッシュアップにも使う。**メインセッション（親）はオーケストレーションに徹し、本文の執筆・参考資料の展開・セルフチェックはすべてサブエージェントの新しいコンテキストで行う**。これにより 1 セッションのコンテキストを圧迫せずに Part・教材全体の量産を完走できる。

> 設計出自: spec 駆動開発ツール cc-sdd v3 の `/kiro-impl`（タスク単位に fresh な implementer / reviewer / debugger を回し、親は起動・厳密パース・状態更新・コミットだけを行う自律実装ループ）の執筆移植。対応: タスクリスト＝PROGRESS.md 進捗表 / 仕様書＝OUTLINE.md（ゴール・骨子）/ implementer＝執筆サブエージェント / reviewer＝independent-reviewer / debugger＝診断サブエージェント。

## 原則（コンテキスト経済）

- **親は Section 本文・参考資料の生テキストを Read しない**。扱うのはファイルパス・定型報告・機械検証の出力だけ。各タスク完了後、以後のタスクで参照するのは1行サマリ（例: `2-1: APPROVED（修正1回）・commit abc1234`）のみとし、報告の詳細を後続の判断に持ち込まない
- **サブエージェントへは常にパスで渡す**（writing.md・様式/学習モデルのリファレンス・OUTLINE・ブリーフ・前後 Section・対象パス）。OUTLINE は「パス＋Section 番号」で渡し、ゴール・骨子・執筆ノートの内容を親が転記しない（/write「サブエージェントに分担させる場合の情報の渡し方」を全面適用する）
- **1 タスク = 1 執筆サブエージェント**。複数 Section を1体にまとめて委任しない（wave 内の並列起動は可。それぞれ独立タスクとして扱う。例外は「4. 完走処理」のやってみよう追加パスのみ）
- **定型報告は厳密にパースする**: `STATUS:` / `VERDICT:` / `DIAGNOSIS:` 等の定型フィールド行だけを結果として扱い、散文からの推測はしない。フィールドが欠落していたら再要求は1回だけ（それでも欠落なら不合格として扱う）
- **状態はディスク上に置く**: `PROGRESS.md`（進捗表）と git（Section 単位コミット）へ毎タスク記帳する。親は累積記憶に依存せず、**各タスク開始時に PROGRESS の該当行を読み直す**。コンテキスト圧縮・セッション中断が起きても、同じスコープで /write を再実行すれば未完タスクだけが再構成され、そのまま再開になる

## 0. 事前条件

- /write「1. 準備」のゲート検査を通過している（G4 済み・スコープ全 Section の見出し骨子が承認済み。未充填の Chapter があれば /outline <Chapter> を先に案内して停止）
- PROGRESS 進捗表と実ファイルの乖離が疑われる場合、それが量産ループの中断由来（未記帳の書きかけ）なら /status を挟まず、同じスコープの再実行で回収する（「1. ランプラン」のタスク再構成が正。/status の実ファイル同期は残工程タスクの検出材料を消しうる）。それ以外の乖離のみ先に /status で同期する

## 1. ランプラン（ユーザー承認は開始時の1回だけ）

1. OUTLINE.md と PROGRESS.md からタスクリストを作る（1 Section = 1 タスク）。**対象は依頼の種別で決まる**:
   - **新規執筆**（未執筆分の量産・`全て` / `残り全部`）: スコープ内の未完 Section が対象
   - **更新・ブラッシュアップ**（既存 Section の一括改稿）: スコープ内の**全 Section** が対象（実ファイルが既存でも除外しない）。改稿指示はランプランに明記し、各タスクのプロンプトへ渡す。対象にできるのは /write トリアージを通過する表現・品質の改稿だけ（Section の増減・改番・複数 Section にまたがる方針・用語の変更は /revise の変更管理で扱い、量産ループでは扱わない）

   **完了・未完は実ファイルの有無ではなく PROGRESS で判定する**: 「draft ✅ かつ review ゲート充足（section: review 列 ✅ / chapter: その Chapter のレビュー実施済み）」を完了とする。実ファイルがあるのに記帳が欠けている Section は**残工程タスク**（執筆をスキップし、「3. タスクサイクル」の機械検証→レビュー→記帳→コミットから実施）として積む。review_gate=chapter で全稿 draft ✅・Chapter レビュー未実施なら **Chapter レビュータスク**を積む（中断再開時にレビューが取り残されるのを防ぐ）。`保留` の Section はユーザーが明示的に解除するまで対象外
2. OUTLINE の `前提:`・`依存:` フィールドから wave（並列可能なグループ）を組む。`依存:` が未記入の Section は `前提:` のみで判定し、どちらも無ければ**逐次に倒す**（並列にしない）。並列可否は /write「3. 執筆」の並列5条件に従い、逐次前提の題材（実践プロジェクトの積み上げ・weave の状態連鎖）は全タスク逐次にする
3. **配布物の正準化**: 全タスクに共通で渡すパス一式（writing.md / config.style・section_model・verification_model に応じたリファレンス / OUTLINE / ブリーフ）と検証コマンド（`python3 scripts/lint_curriculum.py`）をここで1度だけ確定し、以降の起動テンプレートに使い回す（診断サブエージェントにも同じ一式を渡す）
4. ランプランを提示する: `| # | Section | 種類 | タスク種別(新規/改稿/残工程) | wave | 備考 |` の表 ＋ ブリーフの単位 ＋ review_gate（config）＋ 停止条件 ＋（separate × tryit_timing=A でスコープが Part 以上のとき）末尾のやってみよう追加パス
5. 承認を1回得たら、以降は完了報告まで自律で回す（質問しない）。執筆子・修正子が STATUS: BLOCKED / NEEDS_CONTEXT を返した場合は診断サブエージェント（「3. タスクサイクル」手順4）に回して RETRY / BLOCK / STOP へ振り分ける。ループを中断するのは診断が STOP を返した場合と、ループ自体が続行不能な環境不備のみ

## 2. ブリーフ（参考資料の整理結果をファイルとして永続化）

/write「1. 準備」の「複数 Section の一括取得・整理」を、チャットに揮発させずファイルにする。

- Chapter ごとに `.claude/state/write-briefs/<chapter-id>.md` へ書く。`<chapter-id>` は curriculums/ の Chapter ディレクトリ名に一致させる（1層教材・Chapter を持たないスコープではスコープ単位で1つ）。gitignore 済みの作業ファイルでありコミットしない
- **作成はランプラン承認後、その Chapter の第1タスク直前に行う**（JIT）。既存のブリーフがあれば再利用し、再開時に二重生成しない
- **作成はサブエージェントへ委任する**（親が素材を読まないため）。RESEARCH.md を裏取りの正とし、OUTLINE の対象 Section の `参考資料` フィールドの範囲で作らせる。/write「1. 準備」の RESEARCH.md・参考資料の読み込みは量産時はこの子が担う（親は読まない）。更新・ブラッシュアップの実行時は改稿指示もブリーフに含める
- ブリーフ子へ渡すもの: RESEARCH.md・OUTLINE.md のパス、対象 Section 番号の一覧、（改稿時）改稿指示、本節の内容要件（①〜③）と転記禁止ヘッダの指定。完了報告には `FORBIDDEN_TERMS:`（本文に出てはいけない内部語・出典ラベルの一覧）を含めさせ、親は「3. タスクサイクル」手順2の横断 grep の検索語に使う（親はブリーフ本体を読まないため、検索語はこの報告経由で得る）
- 内容: ①Section 横断で統一すべき事実（名前パターン・数値・用語）②Section ごとの使用素材（コード・仕様の verbatim 引用と出典）③教材に書かないこと（RESEARCH.md のネガティブリストの該当分）
- ブリーフ冒頭に必ず次を記す: 「このファイルは執筆用の内部資料。**ここに現れる内部用語・記号（出典ラベル・『ブリーフ』等）を本文へ転記しない**」（内部語の本文混入の実例があるため。検収は「3. タスクサイクル」手順2の横断 grep）

## 3. タスクサイクル（Section 1件ごとに完結させる）

```text
執筆サブエージェント → 親の機械検証 → 独立レビュー
  →（REJECTED → 修正サブエージェント → 再レビュー ×最大2 → なお REJECTED なら診断サブエージェント）
  → 記帳・コミット → 1行サマリだけを引き継いで次のタスクへ
```

1. **執筆**: 新しいサブエージェントを起動する。渡すもの＝正準化したパス一式・OUTLINE のパスと対象 Section 番号（ゴール・種類・骨子・執筆ノートは子に読ませる）・ブリーフのパス・前後 Section のパス・完了報告の定型（STATUS / FILES_CHANGED / REFERENCES_CONSULTED / SELF_CHECK / CONCERNS）。/write「4. セルフチェック・完了」の 1〜5（lint 実行・OUTLINE 整合・コード正確性・参考資料照合・AI 臭チェックと自己採点）まで**子側で完了**させる。執筆中に骨子から外れた場合の **OUTLINE 骨子の書き戻しも子の責務**とし、FILES_CHANGED に OUTLINE.md を含めて報告させる。様式・学習モデル・検証モデルのリファレンスが REFERENCES_CONSULTED に無い場合は検収不合格として差し戻す（/write「3. 執筆」の検収条件）。残工程タスクではこの手順をスキップする
2. **親の機械検証**（自己申告を信用しない。ただし本文は読まない）:
   - `python3 scripts/lint_curriculum.py <対象ファイル>`（🔴 が残っていれば差し戻し）
   - 対象ファイルの存在と規模の確認（例: `wc -m`。目安字数から大きく外れていれば CONCERNS と突合）
   - ブリーフ内部語の横断 grep（「ブリーフ」と、ブリーフ子が報告した FORBIDDEN_TERMS が本文へ漏れていないか）
3. **独立レビュー**: `config.review_gate` に従い independent-reviewer を起動する（section: タスクごと / chapter: Chapter 最終タスク完了時に Chapter 全 Section をまとめて1回。/write「4. セルフチェック・完了」の独立レビュー）。REJECTED の場合は REMEDIATION を**新しい修正サブエージェント**に対象パスと共に渡して修正させ、再レビューする（最大2回）。chapter ゲートでは: 修正ラウンドは Chapter 単位で数え（1ラウンド＝指摘対象の Section ごとに修正サブエージェントを分けて依存順に起動）、再レビューは前回指摘と修正内容の一覧を添えて Chapter 全体に掛け直す
4. **診断（3回目も REJECTED、または子が BLOCKED / NEEDS_CONTEXT を返したとき）**: 単発執筆の /write「4. セルフチェック・完了」では3回目の REJECTED をユーザーへエスカレーションするが、量産ループでは診断がこれを置き換え、STOP のみを人間へ渡す。**失敗履歴を渡さない**新しい診断サブエージェントを起動し、正準化したパス一式・最新の指摘・対象ファイル・OUTLINE の該当 Section を渡して根本原因を分類させる（chapter ゲートでは根本原因の Section の特定も診断の仕事）。修正の無限リトライ（同じ表面修正の繰り返し）を構造的に断つための fresh コンテキストであり、報告は定型で受ける: `DIAGNOSIS: RETRY | BLOCK | STOP`・`ROOT_CAUSE:`・`FIX_PLAN:`（RETRY のときのみ）
   - `RETRY`（原因が特定でき、修正方針が具体的）→ FIX_PLAN を新しい修正サブエージェントに渡して**1回だけ**再走 → 再レビュー。なお REJECTED なら BLOCK 扱いに落とす
   - `BLOCK`（原因が Section 単体で解決しない: 骨子・OUTLINE の設計不備、参考資料の不足）→ タスクを**保留**にする。設計不備は上流（/outline・/revise）への差し戻し事項として完了報告へ
   - `STOP`（教材横断の問題・ユーザー判断が必要）→ ループを中断してエスカレーション
5. **記帳**: PROGRESS の draft 列（review_gate=section なら review 列も）を更新する。改稿タスクでは書き直した Section の review 列をいったん空欄に戻し、再レビュー完了時に記入する（古い検収の残存を防ぐ。/revise の「review 列リセット」と同じ扱い）。Section 単位でコミットする（/write「4. セルフチェック・完了」の完了処理。**stage するのは対象 Section と骨子書き戻し分の OUTLINE.md の明示パスのみ**。`git add -A` は使わない。ブリーフ・一時ファイルは含めない）。保留にしたタスクは PROGRESS の draft 列を `保留` とし（review 列は空欄のまま）、**書きかけの稿はコミットせず**、未コミットパスとして完了報告に明示する。理由は OUTLINE 末尾の執筆ノートに1行残す。子が報告した横断的決定（CONCERNS 内の用語・題材の決定）も執筆ノートへ前送りする（後続タスクの子は OUTLINE 経由でこれを読む＝学習の伝搬）。再開時の Chapter レビュータスクは、指摘ゼロならコミットを作らず review 列の一括記入のみ・修正が出たら該当 Section ごとに修正コミットを作る

wave 内の並列起動は最大3。並列時も機械検証・レビュー・記帳・コミットはタスクごとに独立して完結させる（コミットは親が直列に行う。レビュー待ちの間に次タスクの執筆を開始してよい）。保留タスクに依存する後続タスクは着手せず、依存しないタスクは続行する。

## 4. 完走処理

- （separate × tryit_timing=A・スコープ Part 以上）やってみよう追加パスを最後の1タスクとして実行する（/write「3. 執筆」の A 手順。専用コミット・その場で実行検証）。複数 Section を1パスで編集する「1タスク=1 Section」原則の例外であり、検収は lint（親が実行）と A 手順の実行検証（子に実行コマンドと出力の verbatim 添付を義務づけ、疑わしければ handson-verifier で追試する）で行う（独立レビューは完走後の上位スコープ /review に委ねる）。`保留` の Section は追加パスから除外し、OUTLINE 付録のやってみよう表に「保留」と記す
- 完了報告: `| Section | 執筆 | レビュー判定 | 修正回数 | commit |` の表 ＋ 保留と上流差し戻し事項（未コミットの書きかけ稿のパスを含む）＋ 生成したブリーフのパス ＋ 次アクションの提案（上位スコープの /review、📸 が残っていれば /capture 等）
- **完了主張は証拠の範囲まで**（/write「4. セルフチェック・完了」の完了処理）: 「全タスク APPROVED」と言えるのは、親が lint と独立レビューの判定を実際に確認したタスクだけ。サブエージェントの成功報告そのものは証拠にしない
- **再開**: 中断後に同じスコープで /write を再実行すれば、「1. ランプラン」手順1のタスクリスト構成が PROGRESS（draft・review 両列）と実ファイルから未完タスク・残工程タスクだけを拾い、続きから回る（完了済みタスクの成果には触れない）
