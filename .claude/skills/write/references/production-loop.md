# 量産ループ（複数 Section の一括執筆プロトコル）

`/write` が複数 Section を含むスコープ（Chapter・Part・`全て`）を扱うときの実行プロトコル。**メインセッション（親）はオーケストレーションに徹し、本文の執筆・参考資料の展開・セルフチェックはすべてサブエージェントの新しいコンテキストで行う**。これにより 1 セッションのコンテキストを圧迫せずに Part・教材全体の量産を完走できる。

> 設計出自: spec 駆動開発ツール cc-sdd v3 の `/kiro-impl`（タスク単位に fresh な implementer / reviewer / debugger を回し、親は起動・厳密パース・状態更新・コミットだけを行う自律実装ループ）の執筆移植。対応: タスクリスト＝PROGRESS.md 進捗表 / 仕様書＝OUTLINE.md（ゴール・骨子）/ implementer＝執筆サブエージェント / reviewer＝independent-reviewer / debugger＝診断サブエージェント。

## 原則（コンテキスト経済）

- **親は Section 本文・参考資料の生テキストを Read しない**。扱うのはファイルパス・定型報告・機械検証の出力だけ。各タスク完了後に親のコンテキストへ残すのは1行サマリ（例: `2-1: APPROVED（修正1回）・commit abc1234`）のみで、報告の詳細は保持しない
- **サブエージェントへは常にパスで渡す**（writing.md・様式/学習モデルのリファレンス・OUTLINE・ブリーフ・前後 Section・対象パス）。OUTLINE は「パス＋Section 番号」で渡し、ゴール・骨子・執筆ノートの内容を親が転記しない（/write「サブエージェントに分担させる場合の情報の渡し方」を全面適用する）
- **1 タスク = 1 執筆サブエージェント**。複数 Section を1体にまとめて委任しない（wave 内の並列起動は可。それぞれ独立タスクとして扱う）
- **定型報告は厳密にパースする**: `STATUS:` / `VERDICT:` 等の定型フィールド行だけを結果として扱い、散文からの推測はしない。フィールドが欠落していたら再要求は1回だけ（それでも欠落なら不合格として扱う）
- **状態はディスク上に置く**: `PROGRESS.md`（進捗表）と git（Section 単位コミット）へ毎タスク記帳する。親は累積記憶に依存せず、**各タスク開始時に PROGRESS の該当行を読み直す**。コンテキスト圧縮・セッション中断が起きても、同じスコープで /write を再実行すれば未完タスクだけが再構成され、そのまま再開になる

## 0. 事前条件

- /write「1. 準備」のゲート検査を通過している（G4 済み・スコープ全 Section の見出し骨子が承認済み。未充填の Chapter があれば /outline <Chapter> を先に案内して停止）
- PROGRESS 進捗表と実ファイルの乖離が疑われる場合は、先に /status で同期する（タスクリストの正を壊さない）

## 1. ランプラン（ユーザー承認は開始時の1回だけ）

1. OUTLINE.md と PROGRESS.md からタスクリストを作る（1 Section = 1 タスク。draft ✅・保留・実ファイルが既存の Section は対象外）
2. OUTLINE の `前提:`・`依存:` フィールドから wave（並列可能なグループ）を組む。`依存:` が未記入の Section は `前提:` のみで判定し、それも無ければ独立とみなす。並列可否は /write「3. 執筆」の並列5条件に従い、逐次前提の題材（実践プロジェクトの積み上げ・weave の状態連鎖）は全タスク逐次にする
3. **配布物の正準化**: 全タスクに共通で渡すパス一式（writing.md / config.style・section_model・verification_model に応じたリファレンス / OUTLINE / ブリーフ）と検証コマンド（`python3 scripts/lint_curriculum.py`）をここで1度だけ確定し、以降の起動テンプレートに使い回す
4. ランプランを提示する: `| # | Section | 種類 | wave | 備考 |` の表 ＋ ブリーフの単位 ＋ review_gate（config）＋ 停止条件 ＋（separate × tryit_timing=A でスコープが Part 以上のとき）末尾のやってみよう追加パス
5. 承認を1回得たら、以降は完了報告まで自律で回す（質問しない）。中断するのは診断が STOP を返した場合と真の BLOCKED（骨子と参考資料の矛盾・環境不備など、推測で埋めてはならない事態）のみ

## 2. ブリーフ（参考資料の整理結果をファイルとして永続化）

/write「1. 準備」の「複数 Section の一括取得・整理」を、チャットに揮発させずファイルにする。

- Chapter ごとに `.claude/state/write-briefs/<chapter-id>.md` へ書く（1層教材・Chapter を持たないスコープではスコープ単位で1つ。gitignore 済みの作業ファイルでありコミットしない）
- **作成はサブエージェントへ委任する**（親が素材を読まないため）。RESEARCH.md を裏取りの正とし、OUTLINE の対象 Section の `参考資料` フィールドの範囲で作らせる
- 内容: ①Section 横断で統一すべき事実（名前パターン・数値・用語）②Section ごとの使用素材（コード・仕様の verbatim 引用と出典）③教材に書かないこと（RESEARCH.md のネガティブリストの該当分）
- ブリーフ冒頭に必ず次を記す: 「このファイルは執筆用の内部資料。**ここに現れる内部用語・記号（出典ラベル・『ブリーフ』等）を本文へ転記しない**」（内部語の本文混入の実例があるため。検収は「3. タスクサイクル」手順2の横断 grep）

## 3. タスクサイクル（Section 1件ごとに完結させる）

```text
執筆サブエージェント → 親の機械検証 → 独立レビュー
  →（REJECTED → 修正サブエージェント → 再レビュー ×最大2 → なお REJECTED なら診断サブエージェント）
  → 記帳・コミット → 1行サマリだけ残して次のタスクへ
```

1. **執筆**: 新しいサブエージェントを起動する。渡すもの＝正準化したパス一式・OUTLINE のパスと対象 Section 番号（ゴール・種類・骨子・執筆ノートは子に読ませる）・ブリーフのパス・前後 Section のパス・完了報告の定型（STATUS / FILES_CHANGED / REFERENCES_CONSULTED / SELF_CHECK / CONCERNS）。/write「4. セルフチェック・完了」の 1〜5（lint 実行・OUTLINE 整合・コード正確性・参考資料照合・AI 臭チェックと自己採点）まで**子側で完了**させる。様式・学習モデル・検証モデルのリファレンスが REFERENCES_CONSULTED に無い場合は検収不合格として差し戻す（/write「3. 執筆」の検収条件）
2. **親の機械検証**（自己申告を信用しない。ただし本文は読まない）:
   - `python3 scripts/lint_curriculum.py <対象ファイル>`（🔴 が残っていれば差し戻し）
   - 対象ファイルの存在と規模の確認（例: `wc -m`。目安字数から大きく外れていれば CONCERNS と突合）
   - ブリーフ内部語の横断 grep（「ブリーフ」・出典ラベル等が本文へ漏れていないか）
3. **独立レビュー**: `config.review_gate` に従い independent-reviewer を起動する（section: タスクごと / chapter: Chapter 最終タスク完了時にまとめて1回。/write「4. セルフチェック・完了」の独立レビュー）。REJECTED の場合は REMEDIATION を**新しい修正サブエージェント**に対象パスと共に渡して修正させ、再レビューする（最大2回）。review_gate=chapter の REJECTED で指摘が複数 Section にまたがる場合は、Section ごとに修正サブエージェントを分けて依存順に起動する
4. **診断（3回目も REJECTED のとき）**: **失敗履歴を渡さない**新しい診断サブエージェントを起動し、最新の指摘・対象ファイル・OUTLINE の該当 Section だけを渡して根本原因を分類させる。修正の無限リトライ（同じ表面修正の繰り返し）を構造的に断つための fresh コンテキストであり、判定は次の3値で受ける:
   - `RETRY`（原因が特定でき、修正方針が具体的）→ 修正方針を新しい修正サブエージェントに渡して**1回だけ**再走 → 再レビュー
   - `BLOCK`（原因が Section 単体で解決しない: 骨子・OUTLINE の設計不備、参考資料の不足）→ タスクを**保留**にする。設計不備は上流（/outline・/revise）への差し戻し事項として完了報告へ
   - `STOP`（教材横断の問題・ユーザー判断が必要）→ ループを中断してエスカレーション
5. **記帳**: PROGRESS の draft 列（review_gate=section なら review 列も）を更新し、Section 単位でコミットする（/write「4. セルフチェック・完了」の完了処理。ブリーフ・一時ファイルは含めない）。保留にしたタスクは PROGRESS の draft 列を `保留` とし（review 列は空欄のまま）、理由を OUTLINE 末尾の執筆ノートに1行残す。子が報告した横断的決定（CONCERNS 内の用語・題材の決定）も執筆ノートへ前送りする（後続タスクの子は OUTLINE 経由でこれを読む＝学習の伝搬）

wave 内の並列起動は最大3。並列時も機械検証・レビュー・記帳・コミットはタスクごとに独立して完結させる（コミットは親が直列に行う。レビュー待ちの間に次タスクの執筆を開始してよい）。保留タスクに依存する後続タスクは着手せず、依存しないタスクは続行する。

## 4. 完走処理

- （separate × tryit_timing=A・スコープ Part 以上）やってみよう追加パスを最後の1タスクとして実行する（/write「3. 執筆」の A 手順。専用コミット・その場で実行検証）
- 完了報告: `| Section | 執筆 | レビュー判定 | 修正回数 | commit |` の表 ＋ 保留と上流差し戻し事項 ＋ 生成したブリーフのパス ＋ 次アクションの提案（上位スコープの /review、📸 が残っていれば /capture 等）
- **完了主張は証拠の範囲まで**（/write「4. セルフチェック・完了」の完了処理）: 「全タスク APPROVED」と言えるのは、親が lint と独立レビューの判定を実際に確認したタスクだけ。サブエージェントの成功報告そのものは証拠にしない
- **再開**: 中断後に同じスコープで /write を再実行すれば、「1. ランプラン」手順1のタスクリスト構成が PROGRESS と実ファイルから未完タスクだけを拾い、続きから回る（完了済みタスクの成果には触れない）
