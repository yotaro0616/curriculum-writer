# 教材の執筆ワークフロー

**入力**: $ARGUMENTS

## スコープの解釈

CLAUDE.md の HOW で定義された階層構造に基づいてスコープを判定する（番号のみでも可）。下表は3階層を包含する汎用表で、プロジェクトごとの調整は不要。

| 入力 | 対象 |
|---|---|
| `Part 2`（または `2`） | Part 全体（3層のみ） |
| `Chapter 2-1`（または `2-1`） | Chapter 全体（3層。2層では `Chapter 2` / `2`） |
| `Section 2-1-3`（または `2-1-3`） | Section 単体（2層では `2-3`、1層では `3`） |

`全て` / `残り全部` は全 Section が対象（`curriculums/` に既存ファイルがある Section はスキップ）。

ディレクトリパス・タイトルは CLAUDE.md の命名規則と OUTLINE.md に従う。

## 0. 依頼のトリアージ

着手前に依頼を振り分け、層違いの編集（設計変更なのに本文だけ直す等）を防ぐ。

| 依頼 | 対応 |
|---|---|
| 誤字・リンク切れ・軽微な表現修正 | このワークフローを省略して直接編集（機械的検証のみ実行） |
| 既存 Section の更新・ブラッシュアップ / 新規執筆 | 通常フロー（1〜4） |
| Section の追加・削除・移動・改番、複数 Section にまたがる方針・用語変更、様式ロック後の様式変更 | `/revise` へ（構成変更は連鎖破壊を防ぐため影響範囲7項目を走査する。影響が 1〜2 Section・改番なしなら /revise の軽ゲート＝proposal.md のみで済む） |
| ペルソナ・コンセプト・ゴール（哲学）に関わる変更 | `/revise` へ（最重量クラス） |

## 1. 準備

**ゲート検査（最初に）**: `PROGRESS.md` があれば読む。①複数 Section の量産は G4（様式ロック）後にのみ行う（未了なら `/pilot` を案内。パイロット執筆自体は /pilot 経由のため免除） ②対象スコープの見出し骨子が OUTLINE.md に未充填なら停止し、`/outline <Chapter>` を先に案内する。いずれも `--force` で明示的にバイパスできる（その場合は方針合わせで見出し列をゼロから提示する）。あわせて `config`（決定録。キーの意味は PROGRESS テンプレのコメントを正とする）を読み、以降の執筆判断に適用する。**config.style が emoji 以外なら `.claude/skills/write/references/styles/<style>.md`、config.section_model が weave なら同 `section-models/weave.md`、config.verification_model が ai-delegated なら同 `verification-ai-delegated.md` を必ず Read してから書く**（該当リファレンスが存在しない場合は停止し、/fw-sync（writing.md の手動マージを含む）を案内する）。

1. `CLAUDE.md` を Read し、哲学（ペルソナ・コンセプト・ゴール）と階層構造を確認
2. `OUTLINE.md` を Read し、対象スコープの設計を把握（ゴール、種類、参考資料、前提 Section 等）。末尾に「執筆ノート」節があれば必読し、既往の横断的決定（用語・題材・バージョン）に従う
3. `RESEARCH.md`（/research の調査成果）があれば Read する。トピックマップ・題材・変わりやすい領域・読者仮説を把握し、**以降は RESEARCH.md を裏取りの正**とする（Web 取得は差分・不足分の確認に留める）。RESEARCH.md はトピック全体の調査結果、次の `参考資料` は各 Section が使うその部分集合、という関係
4. **参考資料の取得**（Section 単位）: OUTLINE.md の対象 Section の `参考資料` フィールド（その Section が使う具体的な出典）を確認し、**ローカルファイルパスは Read ツールで読み込む**。URL がある場合は WebFetch、必要に応じて WebSearch でリサーチする。取得した情報から教材に含める数値・仕様・コードパターンを箇条書きで整理し、執筆時は記憶ではなくこの整理結果を参照する。複数 Section をまとめて書く場合は**事前に一括取得して整理結果を1つにまとめ**（重複取得を防ぐ）、Section 横断で統一すべき事実（名前パターン・数値・用語）も含める
5. `curriculums/` に既存ファイルがあればサブエージェントで分析（用語の一貫性、前後との接続）
6. 実践プロジェクトがある場合: Section 間の依存関係（前の Section で作成したコード・設定を後の Section が前提とする箇所）を確認し、整合性を保って執筆する

## 2. 方針合わせ

執筆に入る前に、見出し構成をユーザーに提示して方向性を揃える。Part / Chapter 単位のときは Chapter ごとにまとめる。

**OUTLINE.md に承認済みの見出し骨子がある場合**、方針合わせは骨子の確認・微調整に短縮する（骨子どおりなら「骨子のとおり執筆します」と示すだけでよい。骨子から変える場合は理由を添えて提示し、承認後に OUTLINE の骨子へ書き戻してから執筆する）。

- **構成判断**: 対象スコープの各 Section について、見出しを Why → What → How の流れで箇条書きに列挙して提示する（1行サマリーで済ませず、実際の見出し単位で出す）。見出しは writing.md「見出しの設計」の規律5項目と `config.arc_mode`（決定録）に従う。OUTLINE.md の設計から外れる場合は理由を添える
- **接続の確認**: 最終 Section の接続先（次 Section / 次 Chapter / 次 Part / 教材の締め括り）を明示的に確認する
- **不明点**: 判断に迷う点があれば質問する

ユーザーの反応を受けてから執筆に入る。

## 3. 執筆

CLAUDE.md の哲学を踏まえ、`.claude/rules/writing.md` のルール・テンプレートに沿って書く。Part / Chapter 単位など複数 Section を含む場合は、含まれる全 Section を順に執筆する（サブエージェントへの分担も可）。

**概念 Section の「やってみよう」**: `config.tryit_timing`（決定録）に従う（weave では N/A: 概念 Section に置く場合のみ B 扱いで書く）。
- **A（Part 単位2パス）**: 本文執筆では書かない。Part 初稿完了直後に、OUTLINE 付録「やってみよう表」（対象節 / 題材 / 見せる機能）を設計してから一括追加する。追加パスは専用コミットにし（他変更と混載しない）、各件をその場で実行検証し、冒頭 💡 宣言の差し替えまで行う。完了時に表と本文（実践見出し「やってみよう:」の grep。emoji 様式は `## 🏃 やってみよう:`、他様式は `## やってみよう:`）を照合し、未展開が残っていないか確認する
- **B（同一パス）**: 本文と同時に書き、その場で実行検証する

**画面キャプチャ（config.capture を使う教材）**: 執筆時に、writing.md「画像」の密度4類型に該当する位置へ 📸 撮影指示コメントを1行で埋める（OUTLINE の `画面:` フィールドがあればそれを展開する）。撮影は行わない（/capture が後から一括で行う）。

**サブエージェントに分担させる場合の情報の渡し方**:

- **ファイルパスで渡す**: ルールファイル（`.claude/rules/writing.md`）、OUTLINE.md、参考資料のローカルファイルはパスを渡してサブエージェント自身に Read させる。**config.style が emoji 以外・section_model が weave・verification_model が ai-delegated の教材では、該当リファレンス（styles/<style>.md・section-models/weave.md・verification-ai-delegated.md）のパスも必ず渡し、完了報告の REFERENCES_CONSULTED に含まれていることを検収条件にする**（渡し漏れると子エージェントが emoji・二段構成の既定規範だけで書いてしまう）。プロンプトへのルール要約やコード全文の埋め込みは避ける
- **記憶からの再構成を禁止する**: 参考コードは必ず Read 結果からコピーする。メインエージェントの要約を経由させない
- **数値はソースで検証させる**: 個数・件数等の数値を記載する場合、参考資料の整理結果をそのまま使わず、実ファイルを Read してカウントを検証するよう指示する
- **セクションタイトルは正確に引用させる**: 前提知識や接続文でセクション名を参照する際は OUTLINE.md のタイトルを正確に使い、要約・言い換えをしないよう指示する
- **完了報告は定型フォーマットで受け取る**: 次のフィールドで報告させ、これ以外の自由文の自己申告は成果の根拠として扱わない
  - `STATUS:` READY_FOR_REVIEW / BLOCKED / NEEDS_CONTEXT
  - `FILES_CHANGED:` 変更ファイル一覧
  - `REFERENCES_CONSULTED:` 実際に Read / WebFetch した参考資料（パス・URL）
  - `SELF_CHECK:` セルフチェック項目の実施結果
  - `CONCERNS:` 判断に迷った点・要確認事項
- **並列起動は次の5条件を満たす Section のみ**（満たさなければ依存順に逐次実行）: ①相互に概念依存がない ②同一ファイルを触らない ③逐次前提の題材（実践プロジェクトの積み上げ等）でない ④前提 Section が完了済み ⑤扱う範囲（境界）が重ならない。OUTLINE の前提フィールドから依存の層（wave）を組み、同一 wave 内のみ並列にする

## 4. セルフチェック・完了

以下を検証し、問題があれば修正する:

1. **機械的検証**: `python3 scripts/lint_curriculum.py <対象ファイル>` を実行し、指摘をすべて解消する（検出パターンの正はスクリプト側。編集時にも PostToolUse hook が同じ検査を自動実行する）
2. **OUTLINE との整合**:
   - 各 Section の末尾接続文が、OUTLINE.md の次 Section のゴールキーワードを網羅しているか
   - OUTLINE の `前提:` フィールドが `📝 **前提知識**` として反映されているか
   - 本文が OUTLINE のゴールの範囲内に収まっているか（ゴールにないトピックを追加していないか）
3. **コードの正確性**（実践プロジェクトを扱う場合）:
   - ファイルパスが実在すること
   - クラス名・メソッド名・変数名が実ファイルと一致すること
   - 簡略化したコードに「抜粋」注記があること
   - 数値（個数・件数）が実ファイルと一致すること
4. 参考資料との照合: 教材に記載した数値・仕様が準備で整理した内容と一致するか確認
5. **AI 臭チェック（最後に必ず）**: `.claude/skills/review/references/ai-slop-curriculum.md` の語彙チェックと 🧠 コラム専用基準で本文を点検し、該当箇所を修正する（談話レベル全体（構造・立場）の検査は /review の責務として二重適用しない）。仕上げに**採点5軸を自己採点し、各軸の点数と根拠1行を完了報告に含める。合計 35/50 未満なら書き直してから次へ進む**。教材の文体（敬体・断定）を崩す原典ルール（中間温度・伝聞化・毒）は適用しない
6. **独立レビュー**: `config.review_gate`（決定録）に従う。**section（既定）**: Section 執筆パスごとに `.claude/agents/independent-reviewer` をサブエージェントとして起動し、実ファイルのみを根拠に検証させる。REJECTED の場合は REMEDIATION に沿って修正して再依頼する（最大2回。3回目も REJECTED ならユーザーにエスカレーションする）。**chapter**: Section 単位では起動せず、Chapter の最終 Section 完了時に Chapter 全体をまとめて1回検証させる（PROGRESS の review 列も Chapter レビュー完了時に一括記入し、それまでの Section は「執筆済み・未レビュー」として扱う）。軽微修正（トリアージで省略した場合）はこのゲートを省略してよい
7. **完了処理**:
   - **完了主張は証拠の範囲まで**: 「完了」と報告してよいのは、この執筆パスで実際に検証した範囲だけ。サブエージェントの完了報告・過去に通ったチェック・ファイルの存在は完了の証拠にしない（必要なら再検証する）
   - **見出し骨子の書き戻し**: 執筆中に骨子から外れた場合、本文の完成と同時に OUTLINE.md の骨子を実態へ更新する（設計と本文を乖離させない）
   - **執筆ノートの前送り**: 執筆中に下した横断的決定（用語の表記・選んだ題材・バージョン固定・避けた表現）を OUTLINE.md 末尾の「執筆ノート」節に1行ずつ追記する
   - **進捗の記録**: `PROGRESS.md` があれば、対象 Section の draft 列を更新する
   - **コミット**: この執筆パスの成果物のみでコミットする（例: `curriculums(2-1): ...`）。画像・動画の変更と混載しない
   - セルフチェックと独立レビューの結果を報告し、上位スコープ完了時は `/review` の実行を提案する
