# capture - スクリーンショットの一括撮影・挿入

/write が本文に埋めた撮影指示コメントを、Playwright で実行して画像に差し替える。**執筆と撮影を分離する**ことで、本文は先に完成させ、画像は環境が整った時点でまとめて撮れる。

撮影指示コメントの書式（/write が埋める。詳細は writing.md「画像」）:

```text
<!-- 📸 capture: <URLまたは対象画面> / <再現手順（前提 Step・クリック・入力等）> / <静止画|gif> -->
```

**入力**: $ARGUMENTS（スコープは /write と同じ解釈。省略時は `curriculums/` 全体から 📸 残存ファイルを検索する）

## 1. 撮影計画の提示

1. 対象ファイルから 📸 コメントを全件抽出する（Grep: `<!-- 📸`）。**直後に画像参照が既にあるものは撮影済み**としてスキップする（lint の `capture-pending` と同じ判定。再撮影は明示依頼時のみ）
2. 計画表を提示する: `| # | ファイル:位置(見出し) | 対象 | 再現手順 | 種別 | 判定(実行/スキップ/BLOCKED) |`
3. **撮影スキップの基準**: 計画したファイル名の画像が `assets/screenshots/` に既に存在する場合は撮影をスキップし、挿入のみ行う（ユーザーが手動撮影した画像の取り込みもこの経路で行える）
4. **BLOCKED の基準**: 認証・ログインが必要 / 課金操作を伴う / 破壊的操作を伴う / 対象がローカルアプリ・エディタ・ターミナル画面（Playwright で撮れない） / 再現手順の前提状態（「Step N まで実施済み」等）を再現する手段がない。BLOCKED は理由と**保存先パスの指定**付きでユーザーに引き継ぐ（手動撮影 → 再実行で取り込み）
5. 計画をユーザーに確認してから撮影に進む（ブラウザ操作を伴うため確認をスキップしない）

## 2. 撮影（Playwright）

1. Playwright MCP ツール（`mcp__playwright__*`）を ToolSearch でロードして使う（browser_navigate / browser_snapshot / browser_take_screenshot / browser_click / browser_type 等）
2. 各指示について: 対象を開く → 再現手順を実行 → 撮影
3. **静止画**: `assets/screenshots/<section番号>/<連番2桁>-<内容の英語スラッグ>.png` に保存（例: `assets/screenshots/2-1/01-welcome-page.png`）
4. **GIF**: 操作の各ステップを連番スクショで撮り、`ffmpeg` があれば GIF に変換して同じ命名で `.gif` に保存。ffmpeg が無い・変換品質が不十分な場合は BLOCKED 扱いで報告し、手動録画を提案する
5. 撮影のリトライは同一対象につき最大2回。それでも意図した画が撮れなければ BLOCKED

## 3. 異常検知（重要）

撮影対象が**想定外の画面状態**（エラー画面・空白・レイアウト崩れ・ログイン要求・意図と異なる内容）だった場合は、**撮影せず停止してユーザーに確認する**。「それらしい別画面」で進めない。教材の記述と実画面が食い違っている場合は、撮影より先に本文の誤りの可能性を報告する。

## 4. 挿入と検収

1. 撮影（または既存画像の検出）に成功した項目について、**📸 コメントは削除せず**、その直後に captured スタンプと画像タグを挿入する（📸 コメントが「再撮影レシピ」として残り、鮮度管理・撮り直しの単一ソースになる）:

   ```markdown
   <!-- 📸 capture: <対象> / <再現手順> / <静止画|gif> -->
   <!-- captured: YYYY-MM-DD <環境・アプリのバージョン> -->
   ![<alt テキスト>](<相対パス>/assets/screenshots/<section番号>/<ファイル名>)
   ```

   - 再撮影時は画像ファイルを同名で上書きし、captured スタンプの日付を更新する（本文参照を壊さない）
   - **相対パスは階層構造に依存する**（/illustrate と同じ規約: 3層 `../../../assets/...`、2層 `../../assets/...`、1層 `../assets/...`）
   - **alt は画像の内容を説明する日本語**で必ず書く（「〜の画面」等）。キャプションの要否・書式は様式に従う（`PROGRESS.md` config.style の様式リファレンス参照）
2. 検収: `python3 scripts/lint_curriculum.py <対象ファイル>` を実行し、`capture-pending` / `image-alt-missing` / `image-file-missing` が解消したことを確認する。ファイルサイズを確認する（1枚 3MB 超は圧縮を検討して報告）。撮影した画像に個人情報・トークン・実在の組織名等が写り込んでいないか挿入前に目視確認する。疑わしければ BLOCKED
3. 結果報告: `| # | 状態(✅/スキップ/BLOCKED) | 保存先 | 備考 |` + BLOCKED の引き継ぎ事項（保存先パス指定つき）
4. **コミット**: このパスの成果物のみ（画像 + 挿入タグ。例: `capture(2-1): スクリーンショットを撮影・挿入`）。本文執筆・図・動画の変更と混載しない
5. `PROGRESS.md` があれば図列の扱いに従い進捗を更新する（📸 の残存は /status が未着手として報告する）

## 規律

- **役割分担**: 概念図（メンタルモデルの可視化）は `/illustrate`、実画面のキャプチャは本スキル。1つの Section に両方があってよい
- **積み上げ型ハンズオンの中間状態**: アプリを段階的に作る教材では、📸 の再現手順に「どの Step まで実施済みの状態か」が明記されている前提で動く。その状態を Playwright だけで再現できない場合は BLOCKED とし、ユーザーの手元の実装で撮る手順（保存先パス指定）を案内する
- **ローカルアプリの画面**（エディタ・ターミナル等）は Playwright で撮れないため常に BLOCKED とし、手動スクショを依頼する
- 撮影を伴わない再実行は安全（📸 が残っていなければ「対象なし」と報告して終了する）
