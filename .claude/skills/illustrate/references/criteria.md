# 中心概念とタイプの選定ガイド

Part 1〜4 の概念 Section には **1 枚ずつ画像を入れる** のが基本方針。
したがってここでの判断は「画像を入れるか否か」ではなく、**「その Section の何を・どのタイプで描くか」** である。

## 1. 中心概念を 1 つ選ぶ

画像は導入の 🧠（先輩エンジニアはこう考える）の直後に置かれる。読者が Section を開いて最初に出会う図なので、**この Section で一番つかんでほしい 1 つのメンタルモデル** を選ぶ。

選び方の指針:

- **サマリー図として描く**: Section 冒頭に置かれ、要点を一目で伝える役割を持つ。プロンプトは `style-guide.md` のテンプレートに従い、構図を具体的に指定する
- **「how it works」ではなく「how to think about it」**: 正確な処理順序やデータの流れは Mermaid（本文中）の役割。画像は「どういう感覚で捉えればいいか」を担う。本文に Mermaid がある概念は、その再描画にせず、別角度（比喩・鳥瞰・Before/After）から描く
- **🧠 の語りに呼応させる**: 導入の 🧠 が使っている比喩・痛み・たとえ話を、そのまま絵にするのが最も効果的（画像が 🧠 の直後に並ぶため、語りと図が響き合う）
- **1 枚 1 概念**: 欲張らない。Section の主役概念だけを描く（要素は 5〜8 個以内）
- **Laravel 対比を活かす**: 本教材の背骨は Laravel 対比。PHP / Laravel の既知 → Java / Spring の新概念、という対比は Before/After や比喩と相性が良い

## 2. 構図を選ぶ（3 つの型）

中心概念が決まったら、どう描くか（構図）を選ぶ。次の 3 つは **構図の引き出しであって、排他的な分類ではない**。1 枚が複数を兼ねてよい（例: 比喩を使った対比図）。

| # | 構図 | どう描くか | 向く概念（本教材の例） |
|---|------|------|--------|
| 1 | **比喩図（メンタルモデル）** | 抽象概念を日常の物・場面に置き換え、対応関係をラベルで併記する | DI コンテナ = 倉庫番、ジェネリクス = クッキー型、インターフェース = 契約書、GC = 掃除係 |
| 2 | **対比図（Before/After）** | 左右に分割し、旧→新・課題→解決・PHP→Java・思考の転換を対比する | 静的 vs 動的型付け、Fat Controller → レイヤード、手続き → ポリモーフィズム |
| 3 | **鳥瞰図（地図）** | 全体を街・施設の地図に見立て、各要素を日常の物（銀行・倉庫・取引先等）に擬物化して一望させる | Spring エコシステムの全体像、レイヤードの 3 層 |

各構図の描き方（配色・レイアウト）は `style-guide.md` の「画像の種類別ガイド」を参照する。

## 3. 描きにくい Section の扱い

基本文法など、一見「絵にしにくい」Section もある。その場合でも、必ず次のいずれかの角度が見つかる:

- **導入の課題から Before/After**: 導入は「これがないと何が困るか」から始まる（writing.md）。その課題→解決を対比で描く
- **Laravel 対比そのものを図に**: PHP ではこう、Java ではこう、という対応を比喩・対比で描く
- **Section の鳥瞰**: その Section で学ぶ要素を地図的に並べ、「これから何を学ぶか」を一目で示す

それでも本当に意味のある図が立たない場合は、無理に飾り画像を作らず、plan の報告でその旨を述べてユーザーの判断を仰ぐ。

## plan の報告フォーマット

```markdown
### [Section 番号] [Section タイトル]

- **状態**: 未生成 / 生成済み
- **中心概念**: [図にする 1 つの概念]
- **タイプ**: [3 つの構図のどれか]
- **画像名**: `<section番号>-<concept-slug>`
- **プロンプト概要**: [画像に描く内容の概要]
```
