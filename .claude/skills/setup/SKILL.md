# 上流フェーズのルーター

執筆の前提となる CLAUDE.md（哲学）と OUTLINE.md（設計）に全力を注ぐため、上流を4フェーズ＋承認ゲートに分割している。/setup は状態を見て次のフェーズを案内する。

```text
/research ──G1 調査結論──→ /define ──G2 哲学──→ /outline ──G3 構成──→ /pilot ──G4 様式ロック──→ /write 量産
（RESEARCH.md）             （CLAUDE.md）        （OUTLINE.md 骨格）    （writing.md 確定＋試作）
                                                      ↑
                                     /outline <Chapter> で執筆直前に見出し骨子を充填（JIT）
```

- 人間が承認するのは**ゲートの成果物だけ**（各フェーズ内部の進め方は AI の裁量）
- 裏取り（調査）は上流の責務。/write は RESEARCH.md の参照と差分確認に留まる

**入力**: $ARGUMENTS

## 手順

1. `PROGRESS.md` を Read する
   - **無い場合（新規教材）**: 教材の規模感（トピック・想定 Section 数・書き手の習熟度）を聞き、下の適応的深度を提案 → PROGRESS.md をテンプレートから生成 → `/research` から開始する
   - **有る場合**: ゲート状態から次フェーズを判定して案内する

2. 判定表:

| 状態 | 次のアクション |
|---|---|
| G1 なし | `/research`（light 提案の余地あり） |
| G1 済・G2 なし | `/define` |
| G2 済・G3 なし | `/outline`（骨格設計） |
| G3 済・G4 なし | `/pilot` |
| G4 済 | 量産へ。次に書く Chapter の骨子が未充填なら `/outline <Chapter>`（1層は Section 範囲）→ `/write <Chapter>`（複数 Chapter をまとめるなら `/write <Part>`＝量産ループ） |

3. ユーザーが望めば、案内したフェーズをこの場で続けて実行する（複数フェーズの連続実行も可。ただし**各ゲートの承認は省略しない**。ゲート承認が形骸化すると設計層の手戻りが本文に波及する）

4. **「構成を見直したい」系の依頼の振り分け**:
   - 未公開で影響が対象 Chapter 内に閉じる → `/outline` の再設計
   - 公開後・複数 Section にまたがる・様式ロック後の様式変更 → `/revise`
   - 哲学（ペルソナ・コンセプト・ゴール）に関わる → `/revise`（最重量クラス）

## 適応的深度（規模に応じた省略の提案）

小規模教材にフルパイプラインは過剰。省略しても**ゲートの記録は残す**（PROGRESS の adaptive に理由を記録し、ゲートに「(省略)」と日付を入れる）。**G4 のみ例外**: 省略決定時ではなく、最初の Chapter 執筆直後のミニ較正を終えた時点で実日付を記録する（/pilot「省略」参照。量産解禁の実体を伴わせるため）。

| 規模の目安 | research | pilot |
|---|---|---|
| 大規模（3層・数十 Section） | full | 実施 |
| 中規模（2層） | full または light | 実施を推奨 |
| 小規模（1層・熟知トピック） | light または省略 | 省略可（最初の Chapter 執筆直後にミニ較正を行い G4 を記録） |

## 既存プロジェクトへの後付け（旧フローからの移行）

CLAUDE.md・OUTLINE.md が旧 /setup（一括フロー）で生成済みのプロジェクトでは、PROGRESS.md を後付け生成し、G1〜G4 を「YYYY-MM-DD (旧フロー)」形式で記録する。`config` は既存の writing.md と実際の教材の様式から**転記**して生成する（既定値のまま生成すると lint・skills が読む単一ソースが実様式と食い違う）。**見出し骨子のバックフィルはしない**（今後 /revise や新規執筆の対象になった Chapter だけ /outline <Chapter> で充填する）。
