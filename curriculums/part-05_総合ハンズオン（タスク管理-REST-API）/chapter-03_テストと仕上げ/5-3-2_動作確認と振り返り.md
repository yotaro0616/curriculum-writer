## 導入: 「自分の PC で動く」から「どこでも動く」へ

API は完成し、テストも通りました。最後の仕上げは、これを **自分の PC を離れても動く形** にすることです。4-3 で学んだとおり、設定をコードから切り離して環境ごとに与えられるようにし（プロファイル・環境変数）、アプリを 1 つの成果物（実行可能 jar、そして Docker イメージ）にまとめます。秘密の値（JWT の鍵・DB パスワード）はコードに焼き込まず、外から注入します。

これができると、「私の環境では動くのに」という言葉から卒業できます。Laravel で `.env` と Docker（Sail）を使い、環境ごとに設定を変えて動かした経験が、そのまま Spring Boot のプロファイルと Docker パッケージングに地続きでつながります。

### 🧠 先輩エンジニアの思考プロセス

> 仕上げで私が必ず確認するのは「秘密の値がコードやログに漏れていないか」です。JWT の鍵、DB パスワード、トークンそのもの。これらをうっかりログに出したりリポジトリにコミットしたりする事故は、現場で本当に起きます。本教材では鍵を環境変数で外から渡す形にしてあるので、この型を守れば大きな事故は防げます。

> もう一つ、Docker イメージにする価値を実感したのは、新しいメンバーが入ったときでした。「これを動かして」と Docker Compose のファイルを渡すだけで、JDK の版も DB も含めて同じ環境がすぐ立ち上がる。環境構築の説明に半日かけていたのが、コマンド一つになりました。アプリを成果物として固める、というのはそういう実利があります。

## 🏃 実践: 仕上げと片付け

### 🏃 Step 1: 本番向けの設定を整える

4-3-2 で学んだプロファイルで、本番向けの設定を別ファイルに用意します。本番ではスキーマを勝手に変更しないよう `ddl-auto` を `validate` にし、ログは `info` に絞り、SQL は出しません。

```yaml
# src/main/resources/application-prod.yml
spring:
  jpa:
    hibernate:
      ddl-auto: validate     # 本番は検証のみ（スキーマを勝手に変えない）
    show-sql: false
logging:
  level:
    com.example.taskapp: info
```

秘密の値は、3-1-3 / 4-3-2 で学んだ環境変数で外から注入します。`application.yml` の `app.jwt.secret: ${JWT_SECRET:...}` と `spring.datasource.*` は、環境変数 `JWT_SECRET` / `SPRING_DATASOURCE_PASSWORD` などで上書きできます（リラックスバインディング）。

⚠️ **秘密情報はログに出さない**: 4-3-1 で学んだとおり、パスワード・トークン（JWT を含む）・`Authorization` ヘッダーはログに出してはいけません。本アプリのログは「タスクを作成しました: id=…」のような業務の節目（INFO）にとどめ、秘密の値を含めていないことを確認します。

💡 **本番のスキーマ管理は次のステップ**: `ddl-auto: validate` は「テーブルがある前提で構造を検証するだけ」です。本番では Flyway や Liquibase といったマイグレーションツールでスキーマを管理するのが定石ですが、これは本教材のスコープ外（修了後の発展領域）です。次の Docker 起動では、手軽さを優先して既定プロファイル（`ddl-auto: update`）のまま動かします。

### 🏃 Step 2: 実行可能 jar をビルドする

3-1-2 / 4-3-2 で学んだとおり、`spring-boot-maven-plugin` が `package` フェーズで実行可能 jar を作ります。

```bash
# テストも走った上で、実行可能 jar が target/ に生成される
./mvnw package
```

`target/taskapp-0.0.1-SNAPSHOT.jar` が成果物です。これは依存ライブラリと組み込み Tomcat まで同梱しているので、`java -jar` だけで単独起動できます（4-3-2 のレイヤー化された jar）。

### 🏃 Step 3: Docker イメージにパッケージングする

4-3-2 で学んだ `Dockerfile`（マルチステージ・レイヤー展開）を用意します。`jarmode=tools` で jar を層に展開し、変更頻度の低い依存を先に、頻繁に変わるアプリのコードを後にコピーします。

```dockerfile
# Dockerfile
# --- ビルド用ステージ: JAR を層ごとに展開する ---
FROM eclipse-temurin:21-jre AS builder
WORKDIR /builder
ARG JAR_FILE=target/*.jar
COPY ${JAR_FILE} application.jar
RUN java -Djarmode=tools -jar application.jar extract --layers --destination extracted

# --- 実行用ステージ: 展開した層を順にコピーする ---
FROM eclipse-temurin:21-jre
WORKDIR /application
COPY --from=builder /builder/extracted/dependencies/ ./
COPY --from=builder /builder/extracted/spring-boot-loader/ ./
COPY --from=builder /builder/extracted/snapshot-dependencies/ ./
COPY --from=builder /builder/extracted/application/ ./
ENTRYPOINT ["java", "-jar", "application.jar"]
```

⚠️ **`jarmode=tools`（古い記事に注意）**: jar を層に展開するコマンドは、Spring Boot 4 では `java -Djarmode=tools -jar application.jar extract --layers --destination extracted` です。Spring Boot 3.2 以前の `-Djarmode=layertools` という古い書き方の記事が大量に残っているので、混同しないでください（4-3-2）。

アプリと MySQL を一緒に起動できるよう、5-1-2 の `compose.yaml` にアプリのサービスを足します。アプリはコンテナ間ネットワークで `mysql` というホスト名で DB に接続し、秘密の値は環境変数で渡します。

```yaml
# compose.yaml（app サービスを追加）
services:
  mysql:
    image: mysql:8.4
    environment:
      MYSQL_DATABASE: taskapp
      MYSQL_USER: taskuser
      MYSQL_PASSWORD: secret
      MYSQL_ROOT_PASSWORD: rootsecret
    ports:
      - "3306:3306"
    volumes:
      - taskapp-mysql-data:/var/lib/mysql

  app:
    build: .                       # 同じディレクトリの Dockerfile からビルド
    ports:
      - "8080:8080"
    environment:
      SPRING_DATASOURCE_URL: jdbc:mysql://mysql:3306/taskapp   # ホスト名はサービス名 mysql
      SPRING_DATASOURCE_USERNAME: taskuser
      SPRING_DATASOURCE_PASSWORD: secret
      JWT_SECRET: a-strong-production-secret-at-least-32-bytes  # 秘密の鍵を外から注入
      # SPRING_PROFILES_ACTIVE は指定せず、既定プロファイル（ddl-auto: update）で起動する
      # （prod プロファイル＝validate は Step 1 のとおり、スキーマ作成後に切り替える検証用）
    depends_on:
      - mysql

volumes:
  taskapp-mysql-data:
```

ビルドして起動します。

```bash
./mvnw package              # 先に jar を作る（Dockerfile が target の jar を使う）
docker compose up --build -d   # app イメージをビルドし、app と mysql を起動
```

💡 **Dockerfile を書かない選択肢**: 4-3-2 で触れたとおり、Spring Boot 推奨の Buildpacks（`./mvnw spring-boot:build-image`）なら Dockerfile なしでイメージを作れます。本教材では中身が見える Dockerfile を採りましたが、現場ではどちらも使われます。

### 🏃 Step 4: エンドツーエンドで動作を確認する

コンテナで起動したアプリ（`http://localhost:8080`）に対して、通しで叩きます。

```bash
# 登録 → ログイン → トークン取得 → タスク作成 → 一覧
curl -X POST http://localhost:8080/api/auth/register -H "Content-Type: application/json" \
  -d '{"username":"alice","email":"alice@example.com","password":"password123"}'

curl -X POST http://localhost:8080/api/auth/login -H "Content-Type: application/json" \
  -d '{"username":"alice","password":"password123"}'
# → {"accessToken":"eyJ..."}

curl -X POST http://localhost:8080/api/tasks -H "Authorization: Bearer eyJ..." \
  -H "Content-Type: application/json" -d '{"title":"最終確認のタスク","tags":["完成"]}'

curl http://localhost:8080/api/tasks -H "Authorization: Bearer eyJ..."
```

画面も確認します。ブラウザで `http://localhost:8080/` を開き、開発者ツールのコンソールでログイン API を呼んで Cookie をセットしてから（5-2-5）、`http://localhost:8080/tasks` を開くと、同じタスクが HTML 一覧で表示されます。JSON を返す API と HTML を返す画面が、1 つのアプリの中で両立していることを確認してください。

### 🏃 Step 5: 後片付け

確認が済んだら、起動中のコンテナを止めます。

```bash
# コンテナを停止・削除する（DB のデータはボリュームに残る）
docker compose down

# DB のデータごと完全に消したい場合（ボリュームも削除）
docker compose down -v
```

💡 **プロジェクト自体は成果物**: ここで作ったプロジェクトは、片付けて消すものではなく、あなたが作り上げた **成果物** です。後片付けは「起動中のコンテナを止める」ことを指します。`docker compose down -v` はコンテナと DB のデータを消しますが、ソースコードはそのまま残ります。これまでのコミットも含め、ポートフォリオとして手元に残しておきましょう。

## 教材全体の振り返りと、次のステップ

おつかれさまでした。これで、認証付きのタスク管理 REST API を **ゼロから設計・実装・テスト・パッケージング** するところまでを、自分の手で通しました。

この教材であなたが越えてきた道のりを振り返ります。**Part 1** では、静的型付けという発想の転換を軸に、変数・型・制御構文・メソッド・コレクション・例外まで、Java を読み書きする土台を作りました。**Part 2** では、継承・インターフェース・ポリモーフィズムという本格的なオブジェクト指向と、record・enum・ジェネリクス・Optional・Stream といった現代的な Java を身につけ、設計の土台を固めました。**Part 3** では、DI コンテナの「魔法」を解き明かし、Spring MVC で REST API の縦串を通し、Spring Data JPA でデータ層を組み、Thymeleaf で画面描画にも触れました。**Part 4** では、Spring Security・テスト・運用の土台という、実務に耐える品質を備えました。そして **Part 5** で、それらすべてを 1 つの動くアプリケーションへと統合しました。

最初に確認した「Laravel でできたことは Java でもできる」という地図は、ここまで来て実感に変わったはずです。ルーティングは `@RestController`、Eloquent は JPA エンティティ、FormRequest は DTO + Bean Validation、ミドルウェアと認証は Spring Security、Feature テストは `MockMvc`。あなたが PHP / Laravel で培った Web 開発の考え方は、Java / Spring Boot の世界でそのまま資産になりました。違いは「概念」ではなく「記法と作法」であり、その橋を、あなたはもう自分の足で渡れます。

ここから先には、本教材ではあえて扱わなかった発展領域が広がっています。**マイクロサービスと Spring Cloud**、ノンブロッキングな **リアクティブ（WebFlux）**、本格的な **クラウド運用**、**CI / CD パイプライン** の構築、**Kafka 等のメッセージング**、そして **フロントエンドフレームワークとの連携**。これらは、本教材で身につけた「構造を理解して組み立てる」力があれば、必要になったときに一つずつ自分で学んでいけるものです。スキーマ管理の Flyway / Liquibase のように、今回スコープ外とした実務ツールも、土台ができた今なら無理なく取り込めます。
