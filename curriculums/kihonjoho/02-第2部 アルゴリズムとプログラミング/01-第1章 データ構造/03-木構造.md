## あなたが触れているのは、すべて木構造でできている

ブラウザの DOM、ファイルシステムのディレクトリ階層、JSON のネストした構造、Laravel の Blade テンプレートのコンポーネント階層、`composer.json` の依存関係。これらに共通しているのは、データが「親と子」の関係で階層的に並んでいる、つまり **木構造** （tree）になっていることです。

```javascript
// 例: DOM ツリーをたどる JavaScript
document.body.querySelectorAll('div').forEach(div => {
    div.children.forEach(child => { /* ... */ });
});
```

このコードが「親要素から子要素を辿る」操作になっているのは、HTML が根本的に木構造だからです。本セクションでは、この木構造の理論的な側面を、試験頻出のキーワードとともに整理します。データベースのインデックスが速い理由（B 木）、優先度付きキューが O(log n) で動く理由（ヒープ）、これらを理解する基礎になります。

## 木の基本用語

木構造の議論には固有の用語が多く出てくるため、まず整理します。

- **節** （node、ノード）または **節点** : 木を構成する 1 つ 1 つの要素
- **根** （root、ルート）: 木の最も上にある、親を持たない節
- **葉** （leaf、リーフ）: 子を持たない節
- **親 / 子** : ある節から見て、1 つ上の節が **親** 、1 つ下の節が **子**
- **兄弟** : 同じ親を持つ節同士
- **部分木** （subtree）: ある節とその子孫すべてを集めた、より小さな木
- **次数** （degree）: ある節が持つ子の数
- **深さ** （depth）: 根からその節までの辺の数
- **高さ** （height）: その節から葉までの最長経路の辺の数。木全体の高さは根の高さ

```text
                A (根、深さ 0)
              /   \
             B     C
            / \     \
           D   E     F (葉、深さ 2)
                \
                 G (葉、深さ 3)

木の高さ: 3 (A → B → E → G)
A の次数: 2、B の次数: 2、C の次数: 1
```

> 補足: 「深さ」と「高さ」は逆方向の計測です。深さは根から下に向かって数え、高さはその節から葉までを数えます。試験で混同しやすいので注意してください。

## 二分木：各節が最大 2 つの子を持つ

**二分木** （binary tree）は、すべての節が **最大 2 つの子** を持つ木です。子を「左の子」「右の子」と区別します。次数が常に 0、1、2 のいずれかになる、最もシンプルな木の形です。

```text
       A
      / \
     B   C
    /   / \
   D   E   F
```

二分木にはいくつかの特殊形があります。

- **完全二分木** （complete binary tree）: 最下層を除いて全レベルが完全に埋まっており、最下層は左詰めで埋まっている形。後述のヒープはこの形を保ちます
- **満二分木** （full binary tree）: すべての節が子を 0 個または 2 個持つ形
- **平衡二分木** （balanced binary tree）: 左右の部分木の高さの差が一定以下に保たれている形

n 個の節を持つ完全二分木の高さは **約 log₂ n** で済みます。1,000 個の節でも高さは約 10、100 万個でも約 20。これが、後ほど見る「O(log n) の探索」が成立する根拠です。

## 二分探索木 (BST)：左 < 親 < 右の性質

二分木の中でも、特に「左の子 < 親 < 右の子」という大小関係を保つように構築したものを **二分探索木** （binary search tree、BST）と呼びます。

```text
         8
       /   \
      3     10
     / \      \
    1   6      14
       / \    /
      4   7  13
```

この木では、たとえば 8 の左部分木にはすべて 8 より小さい値（3, 1, 6, 4, 7）が、右部分木にはすべて 8 より大きい値（10, 14, 13）が並んでいます。この性質が、探索を高速にします。

**BST の探索手順** （例: 7 を探す）:

1. 根 8 と比較。7 < 8 なので左の子へ
2. 3 と比較。7 > 3 なので右の子へ
3. 6 と比較。7 > 6 なので右の子へ
4. 7 と一致。発見

各ステップで「左に行くか右に行くか」を選ぶことで、探索範囲が半分ずつ絞り込まれていきます。バランスの取れた BST なら探索は **O(log n)** で完了します。

**挿入と削除** も同じ要領で進みます。挿入は適切な位置まで探索し、見つかった空き場所に新しい節を作るだけ。削除は少し複雑で、削除対象の節が葉なら単に消すだけですが、子が 2 つある場合は「右部分木の最小値」または「左部分木の最大値」と入れ替えてから消す、という工夫が必要です。

| 操作 | 平均 | 最悪 |
|---|---|---|
| 探索 | O(log n) | O(n) |
| 挿入 | O(log n) | O(n) |
| 削除 | O(log n) | O(n) |

**最悪 O(n)** が発生するのは、たとえば既にソート済みの値（1, 2, 3, 4, 5, ...）を順に挿入したとき。木が右にだけ伸びる「串刺し」のような形（連結リストと同じ）になり、性能が劣化します。

```text
1
 \
  2
   \
    3
     \
      4
       \
        5
```

この問題を解決するのが、次に説明する平衡二分探索木です。

## 平衡二分探索木：AVL 木と赤黒木

**平衡二分探索木** （balanced BST）は、挿入や削除のたびに木の形を **自動的にバランスさせる** 仕組みを持つ二分探索木です。代表的な実装に **AVL 木** と **赤黒木** （red-black tree）があります。

- **AVL 木** : 各節で左右の部分木の高さの差を最大 1 に保つ。厳密にバランスを取る
- **赤黒木** : 各節を赤か黒に塗り分け、特定のルールでバランスを調整する。AVL ほど厳密ではないが挿入 / 削除のコストが軽い。Java の `TreeMap`、C++ の `std::map`、Linux カーネルなどで採用

平衡二分探索木の探索 / 挿入 / 削除はすべて **最悪でも O(log n)** に保たれます。

> 補足: 試験で「自動的にバランスを保つ二分探索木」と問われたら、AVL 木か赤黒木を選びます。両者の細かいルールよりも、「常に O(log n) を保つための仕組み」という共通点を押さえておくのが安全です。

## B 木：1 節に複数キーを持つ多分木

これまで見てきたのはすべて「1 節が値を 1 つ持つ」二分木でした。これに対して **B 木** （B-tree）は、 **1 節が複数の値（キー）を持ち、子も複数持てる** 多分木です。

```text
            [ 30 | 60 ]
            /    |    \
      [10|20] [40|50] [70|80|90]
```

B 木の節は「複数のキーで範囲を区切り、それぞれの範囲に対応する子へポインタを持つ」構造です。たとえば値 25 を探すなら「30 より小さい」ので左の子へ、その節の中で 10〜20 の範囲を見て見つからなければ「ない」と判定します。

B 木がデータベースで使われる理由は、ディスク I/O の特性にあります。ディスクからの読み込みは「1 ブロック単位」で行われるため、1 節に多くのキーを詰めるほど 1 回の I/O で多くの情報が得られ、ディスクアクセス回数が減ります。二分木で 100 万件を探すには約 20 回のアクセスが必要ですが、 **B 木なら 3〜4 回程度** で済むケースが多いのです。

**B+ 木** （B-plus tree）は B 木の派生で、葉だけがデータを持ち、葉同士がリンクで連結されている形です。範囲検索（`WHERE age BETWEEN 20 AND 30` のようなクエリ）が高速で、MySQL の InnoDB や Oracle、PostgreSQL のインデックスはほぼすべて B+ 木で実装されています。

> 補足: B 木 / B+ 木の詳細は 5-3-4「ビュー・インデックス・ストアド」で再度扱います。ここでは「DBMS のインデックスは木構造の応用」「1 節が多くのキーを持つことでディスク I/O を最小化している」という 2 点を押さえてください。

## ヒープ：優先度付きキューの内部実装

**ヒープ** （heap）は、 **完全二分木** の形をしており、 **親と子の間に大小関係の制約** がある特殊な木です。2 種類があります。

- **最大ヒープ** （max-heap）: すべての節で「親 ≥ 子」。根が常に **最大値**
- **最小ヒープ** （min-heap）: すべての節で「親 ≤ 子」。根が常に **最小値**

最大ヒープの例:

```text
        10
       /  \
      9    7
     / \  / \
    6  5 3  2
```

ヒープの強みは、 **最大値（または最小値）の取得が O(1)** という点です。根を読むだけで済みます。

挿入の手順:

1. 木の末尾（完全二分木を保つように最下層の左から詰める位置）に新しい値を追加
2. 親と比較し、ヒープ条件（最大ヒープなら親 ≥ 子）を満たさなければ入れ替える
3. 根に達するか条件を満たすまで 2 を繰り返す

削除（最大値の取り出し）の手順:

1. 根の値を取り出す（これが最大値）
2. 末尾の値を根に持ってくる
3. 子と比較し、ヒープ条件を満たさなければ大きい方の子と入れ替える
4. 葉に達するか条件を満たすまで 3 を繰り返す

挿入も削除も「根から葉までの一本道を高々 1 回」辿るので、計算量は **O(log n)** です。前セクションで触れた優先度付きキューは、このヒープを内部実装にすることで enqueue / dequeue を O(log n) で実現しています。

> 補足: ヒープを配列で実装することも一般的です。完全二分木は隙間なく詰まっているため、節を配列の添字で表現できます。添字 i の節に対して、左の子は 2i+1、右の子は 2i+2、親は (i-1)/2 という公式で位置が決まります。

## 木の走査：4 つの順番

木のすべての節を 1 回ずつ訪問する手順を **走査** （traversal）と呼びます。代表的な方法が 4 つあります。次の二分木を例にします。

```text
       A
      / \
     B   C
    / \
   D   E
```

| 走査 | 順序 | 訪問結果 |
|---|---|---|
| 前順 (preorder、行きがけ) | 親 → 左 → 右 | A → B → D → E → C |
| 中順 (inorder、通りがけ) | 左 → 親 → 右 | D → B → E → A → C |
| 後順 (postorder、帰りがけ) | 左 → 右 → 親 | D → E → B → C → A |
| レベル順 (level order、幅優先) | 上の層から下、各層は左から右 | A → B → C → D → E |

二分探索木を **中順走査** すると、値が昇順に並んで出てくるという重要な性質があります。また、前順 / 中順 / 後順はスタック（再帰呼び出しが内部でスタックを使う）で、レベル順はキューで実装します。前セクションで学んだスタック / キューが、木の走査でそのまま使われています。

> よくある誤解: 「前順 = 上から下に訪問」ではありません。前順 / 中順 / 後順は **親を訪問するタイミング** が異なるだけで、いずれも左部分木を先に処理してから右部分木に進む点は共通です。

## 要点

- 木の基本用語: **根** （根）、 **葉** 、親 / 子、 **次数** （子の数）、 **深さ** （根からの距離）、 **高さ** （葉までの最長距離）
- **二分木** は各節が最大 2 つの子。 **完全二分木** の高さは約 **log₂ n**
- **二分探索木** （BST）は「左 < 親 < 右」を保ち、探索・挿入・削除が平均 **O(log n)** 、最悪 **O(n)**
- **平衡二分探索木** （AVL 木・赤黒木）は自動でバランスを保ち、最悪でも **O(log n)** を維持
- **B 木** ・ **B+ 木** は 1 節に複数キーを持つ多分木。DBMS のインデックス実装で広く使われる
- **ヒープ** は完全二分木で「親 ≥ 子」（最大ヒープ）または「親 ≤ 子」（最小ヒープ）を満たす。根が最大値 / 最小値で取得 O(1)、挿入 / 削除 O(log n)。優先度付きキューの内部実装
- 木の走査には **前順** ・ **中順** ・ **後順** ・ **レベル順** の 4 種類。BST を中順走査すると値が昇順に並ぶ
