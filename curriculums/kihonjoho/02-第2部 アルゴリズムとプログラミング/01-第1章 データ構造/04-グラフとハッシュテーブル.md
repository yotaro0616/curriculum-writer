## 1-2-3 のグラフ理論を、いま実装の視点で見直す

Chapter 1-2 で学んだグラフ理論は「頂点と辺で物事のつながりを表現する」数学的な構造でした。Twitter のフォロー関係、Google マップの道路網、Composer の依存関係など、Web 開発のあらゆる場所にグラフが潜んでいることも見てきました。

このセクションでは、その理論をコンピュータ上で **どう表現し、どう走査するか** という実装側の視点に踏み込みます。さらに、PHP の連想配列や JavaScript のオブジェクトといった「キーで値を高速に取り出す」仕組みを支える **ハッシュテーブル** （hash table）を扱います。グラフとハッシュテーブルは異なる性質を持つデータ構造ですが、Web 開発の現場で頻繁に使う「キーで何かを引く」という操作の根幹に共通して関わるため、ここで合わせて整理します。

## グラフのコンピュータ表現：隣接行列と隣接リスト

1-2-3 では、グラフの表現方法として **隣接行列** （adjacency matrix）と **隣接リスト** （adjacency list）を学びました。ここでは計算量・メモリ効率の比較を深掘りします。

**隣接行列** は、頂点数 `V` に対して `V × V` の 2 次元配列を作り、`行列[i][j] = 1`（重み付きグラフなら重みの値）で「頂点 `i` から `j` への辺がある」と表現します。 **隣接リスト** は、各頂点に対して「その頂点と接続している頂点のリスト」を持たせます。

```text
頂点 = {A, B, C, D}、辺 = {A-B, B-C, C-D, A-D}

隣接行列               隣接リスト
     A B C D          A: [B, D]
  A  0 1 0 1          B: [A, C]
  B  1 0 1 0          C: [B, D]
  C  0 1 0 1          D: [A, C]
  D  1 0 1 0
```

PHP の連想配列で隣接リストを書くなら次のようなイメージです。

```php
// 例: 4 頂点のグラフを隣接リストで表現
$graph = [
    'A' => ['B', 'D'],
    'B' => ['A', 'C'],
    'C' => ['B', 'D'],
    'D' => ['A', 'C'],
];
```

それぞれの特性は、頂点数 `V` と辺の数 `E` を使って整理できます。

| 観点 | 隣接行列 | 隣接リスト |
|---|---|---|
| 空間計算量 | O(V²) | O(V + E) |
| 辺の有無の確認 | O(1) | O(degree) |
| 全隣接頂点の列挙 | O(V) | O(degree) |
| メモリ効率 | 辺の有無に関わらず V² 必要 | 辺の数に応じて変動 |

**密グラフ** （dense graph、辺の数が V² に近い）には隣接行列が向き、辺の有無を O(1) で確認できます。 **疎グラフ** （sparse graph、辺の数が V 程度しかない）には隣接リストが向き、メモリ消費を辺数 E に比例した量に抑えられます。

Twitter や Facebook の友達 / フォロー関係は、ユーザ数が数億規模なのに 1 人あたりのフォロー数は数百〜数千程度の疎グラフです。1 億ユーザで隣接行列を作ろうとすると 10¹⁶ セルが必要になり、現実的に扱えません。Web 系の SNS や推薦システムでは、ほぼ常に隣接リストが選ばれます。

> よくある誤解: 隣接行列のほうが「シンプルで速そう」に見えますが、V が大きい疎なグラフでは、メモリ消費が致命的になります。試験では「疎なグラフでメモリ効率が良いのは隣接リスト」と覚えるのが安全です。

## グラフ探索：BFS と DFS

グラフ上で「ある頂点からたどれる全頂点を訪問する」処理を **グラフ探索** と呼びます。代表的な方法が 2 つあり、いずれも前セクション 2-1-2 で学んだスタックやキューがそのまま使われます。

| 探索方法 | 使うデータ構造 | 探索順 | 用途 |
|---|---|---|---|
| 幅優先探索 (BFS) | キュー | 開始頂点に近い順 | 最短経路（重みなし）、SNS の「友達の友達」までの距離 |
| 深さ優先探索 (DFS) | スタック / 再帰 | 1 方向に深く | 連結成分の検出、トポロジカルソート、迷路の探索 |

BFS の手順は「開始頂点をキューに enqueue、dequeue した頂点の未訪問隣接頂点を enqueue、キューが空になるまで繰り返す」です。DFS は同じ処理をスタックに置き換える（または再帰呼び出しで実装する）だけ。同じグラフでも、使うデータ構造を変えるだけで全く異なる探索順序が得られる、というのが構造化された探索の面白さです。

## ハッシュテーブル：キーから O(1) で値を引く

ここまでで線形・階層・つながりの 3 系統を見てきましたが、もう 1 つ、データ構造の核となる仕組みがあります。それが **ハッシュテーブル** （hash table、ハッシュ表）です。配列とは別系統で、 **キーから値を平均 O(1) で取り出せる** という強力な性能を持ちます。PHP の連想配列、JavaScript の `Object` / `Map`、Python の `dict`、Java の `HashMap`、Ruby の `Hash` は、すべて内部でハッシュテーブルが動いています。

```php
// 例: PHP の連想配列。裏側はハッシュテーブル
$user = [
    'id'    => 42,
    'name'  => 'Alice',
    'email' => 'alice@example.com',
];
echo $user['email'];   // 平均 O(1) で取り出される
```

`$user['email']` がほぼ瞬時に値を返すのは、内部でキー `'email'` を **ハッシュ関数** に通して配列の添字に変換し、その添字を直接参照しているからです。

## ハッシュ関数：キーを添字に変換する

**ハッシュ関数** （hash function）は、任意のキーを固定長の整数値（ハッシュ値）に変換する関数です。ハッシュテーブルでは、このハッシュ値を **バケット** （bucket、配列の格納先）の添字として使います。

```text
キー: "alice@example.com"
       ↓ ハッシュ関数 hash()
ハッシュ値: 3792847291
       ↓ % バケット数（例: 16）
バケット添字: 3
```

良いハッシュ関数の条件は、 **均等分散** （キーがバケット全体に偏りなく散らばる）、 **決定性** （同じキーには必ず同じ値を返す）、 **計算が高速** の 3 つです。

> 補足: ハッシュ関数は情報セキュリティで扱う暗号学的ハッシュ関数（SHA-256 など）と概念は同じですが、要求される性質が異なります。ハッシュテーブル用は「速い・均等分散」が最重要で、暗号学的な強度（衝突困難性・一方向性）は必須ではありません。詳しくは Part 7「情報セキュリティ」で扱います。

## 衝突 (collision)：異なるキーが同じバケットを指す

ハッシュ関数の値域はバケット数 M に対して必ず広いため、 **異なるキーが同じバケット添字を指す** ことが発生します。これを **衝突** （collision）と呼びます。

```text
キー "alice"  →  ハッシュ値 ... mod 16 = 3
キー "bob"    →  ハッシュ値 ... mod 16 = 3   ← 衝突
```

ハッシュテーブルが現実に機能するためには、この衝突を扱う仕組みが不可欠です。代表的な方法が 2 つあります。

---

## 衝突解決 1：チェイン法 (separate chaining)

**チェイン法** （separate chaining、連鎖法）は、各バケットに **連結リスト** を持たせ、同じバケットに割り当てられた要素をリストに繋いでいく方法です。

```text
バケット 0: [             ]
バケット 1: [ key1 → val1 ]
バケット 2: [             ]
バケット 3: [ key3 → val3 ] → [ key7 → val7 ]   ← 衝突分はリストで繋ぐ
バケット 4: [ key4 → val4 ]
...
```

検索の手順:

1. キーをハッシュしてバケット添字を求める
2. そのバケットの連結リストを先頭から走査し、キーが一致する要素を返す

衝突がない場合は O(1)、衝突がある場合は O(リストの長さ) になります。 PHP・Java の `HashMap` （Java 8 までは純粋なチェイン法、現在は要素数が多い場合に赤黒木に切り替わる）など、多くの実装で採用されています。

---

## 衝突解決 2：オープンアドレス法 (open addressing)

**オープンアドレス法** （open addressing）は、衝突したら **別の空きバケットを探して** そこに格納する方法です。連結リストを使わず、配列のみで完結します。空きバケットを探す方法には次の 3 つがあります。

- **線形探索法** （linear probing）: 次のバケット、その次のバケット、と順番に空きを探す
- **二次探索法** （quadratic probing）: 1, 4, 9, 16, ... のように 2 乗の幅で探す
- **ダブルハッシュ法** （double hashing）: 別のハッシュ関数で計算したステップ幅で探す

検索時も同じ手順でバケットを辿り、キーが一致するか「空きバケット」に到達するまで探します。Python の `dict` や Ruby の `Hash` などはオープンアドレス法の派生形を採用しています。

| 観点 | チェイン法 | オープンアドレス法 |
|---|---|---|
| 実装 | バケット + 連結リスト | 配列のみ |
| メモリ効率 | リストのポインタ分余計 | 配列のみで完結し効率的 |
| 削除の扱い | リストから消すだけで単純 | 「削除済み」フラグが必要 |
| キャッシュ効率 | リストが散らばるため悪い | 連続メモリで良い |

## 負荷率と再ハッシュ

ハッシュテーブルの性能は **負荷率** （load factor）に大きく依存します。

```text
負荷率 α = 格納されている要素数 ÷ バケット数
```

α が小さい（バケットに余裕がある）うちは衝突が少なく、高速に動作します。一方、α が 1 に近づく（バケットがほぼ埋まる）と、衝突が増えて性能が劣化します。

実装上は、α が一定値（例: 0.75）を超えると、 **バケット数を倍に増やして全要素を新しいバケットに再配置する** **再ハッシュ** （rehashing、リハッシュ）を行います。再ハッシュ自体は O(n) のコストですが、頻度が下がるため **均してみれば** （ならし計算量、amortized）挿入は O(1) に保たれます。

> 補足: 試験では「ハッシュテーブルの平均探索計算量は O(1)」と簡潔に問われることが多いですが、これは「負荷率を適切に管理し、ハッシュ関数が均等分散すること」という前提条件があってこそ成立します。最悪計算量は O(n) です（すべての要素が同じバケットに集中したとき）。

---

## ハッシュテーブルと木構造の使い分け

ハッシュテーブルは平均 O(1) で最速ですが、 **順序を保たない** という制約があります。範囲検索（`WHERE age BETWEEN 20 AND 30` のようなクエリ）や昇順 / 降順での走査が必要な場面では、O(log n) でも順序を保つ二分探索木や B+ 木が選ばれます。MySQL の InnoDB が B+ 木をインデックスに採用しているのは、まさにこの範囲検索を効率的に扱うためです。

---

## 要点

- グラフのコンピュータ表現は **隣接行列** （空間 O(V²)、辺有無確認 O(1)、密グラフ向き）と **隣接リスト** （空間 O(V + E)、辺有無確認 O(degree)、疎グラフ向き）
- グラフ探索は **BFS** （キュー、近い順）と **DFS** （スタック / 再帰、深い方向へ）の 2 種類
- **ハッシュテーブル** はキーをハッシュ関数で添字に変換し、平均 O(1) で探索 / 挿入 / 削除を行う
- 異なるキーが同じバケットを指す **衝突** は避けられず、解決方法には **チェイン法** （連結リストで繋ぐ）と **オープンアドレス法** （線形探索 / 二次探索 / ダブルハッシュ）がある
- **負荷率** （要素数 / バケット数）が高くなったら **再ハッシュ** でバケットを増やして再配置する
- ハッシュテーブルは順序を保たない。順序が必要なら木構造を選ぶ
- PHP の連想配列、JavaScript の `Map`、Python の `dict`、Java の `HashMap` は内部実装がハッシュテーブル
