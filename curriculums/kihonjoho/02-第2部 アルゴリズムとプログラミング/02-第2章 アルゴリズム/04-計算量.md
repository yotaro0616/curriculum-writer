## あなたが書いたコード、何のときに遅くなるのか

開発中はサクサク動いていた処理が、本番のデータ量で急に重くなる経験はありませんか。たとえば次のような PHP のコードを考えます。

```php
// 例: 重複する値があるかを調べる
function hasDuplicate(array $arr): bool
{
    foreach ($arr as $i => $a) {
        foreach ($arr as $j => $b) {
            if ($i !== $j && $a === $b) {
                return true;
            }
        }
    }
    return false;
}
```

10 件なら 100 回程度、1,000 件なら 100 万回、100 万件なら 1 兆回の比較が走ります。データ量が増えるにつれて急速に遅くなるこの増え方を「2 乗オーダ」「O(n²)」と表現します。

このセクションでは、こうした「データ量に対する増え方」を数学的に表現する **計算量** （complexity）の概念を整理します。これまで本章で何度も出てきた「O(n)」「O(log n)」「O(2^n)」の正式な意味を理解しましょう。

## なぜ実行時間（秒）ではなく、オーダで議論するのか

「このアルゴリズムは 0.5 秒で動く」のような実時間は、次の要因に大きく左右されます。

- CPU の性能（クロック周波数、コア数）
- メモリの種類と容量
- 動作している OS とプロセス
- プログラム言語と実装の最適化
- 入力データの偏り

つまり同じアルゴリズムでも、環境が違えば実行時間は 10 倍にも 100 倍にも変わります。一方で「データ量 n が増えたときに、実行時間がどう増えるか」という **増加の傾向** は、環境にほぼ依存しない普遍的な性質です。

そこでアルゴリズムの効率は **オーダ** （order、計算量の規模感）で表すのが一般的です。「O(n)」と書けば「n に比例して時間が増える」、「O(n²)」と書けば「n の 2 乗に比例して時間が増える」という意味になります。

## O 記法（ビッグオー）の定義

**O 記法** （Big-O notation）は、関数の **上界** （upper bound、これ以上は増えない限度）を表します。

形式的な定義はやや厳密ですが、試験で問われるのは次の感覚的な理解で十分です。

> `T(n) = O(f(n))` は、十分大きい n に対して `T(n)` は `c × f(n)` 以下に収まる（c は定数）ことを意味する

つまり、**定数倍や低次の項を無視して、最も支配的な項だけを取り出した表記** です。たとえば `T(n) = 3n² + 5n + 100` という関数があれば、n が大きくなるほど `3n²` の項が支配的になり、`5n + 100` の影響は無視できます。さらに定数 3 も無視して `O(n²)` と表記します。

O 記法の評価ルールをまとめると次の通りです。

- **定数項は無視** : `5` も `1,000,000` も O(1)
- **低次の項は無視** : `n² + n` は `O(n²)`
- **定数倍は無視** : `5n` も `100n` も `O(n)`
- **最も支配的な項のみを残す** : `O(n²) + O(n) = O(n²)`

## Ω 記法（ビッグオメガ）と Θ 記法（ビッグシータ）

O 記法が「上界」を表すのに対して、**Ω 記法** （Big-Omega notation）は **下界** （lower bound、これ以下にはならない最小限度）を表します。

> `T(n) = Ω(f(n))` は、十分大きい n に対して `T(n)` は `c × f(n)` 以上になる（c は正の定数）

最良ケースの解析でよく使われます。たとえば挿入ソートは最良で O(n) になりますが、Ω 記法で「挿入ソートの最良計算量は Ω(n)」とも書けます。

さらに、上界と下界が一致する場合は **Θ 記法** （Big-Theta notation）を使います。

> `T(n) = Θ(f(n))` は、`T(n)` が `f(n)` の定数倍で上からも下からも挟まれることを意味する

マージソートは最良でも最悪でも O(n log n) なので、Θ(n log n) と書けます。

| 記法 | 意味 | 主な用途 |
|---|---|---|
| O(f(n)) | 上界（最悪ケースの解析） | 「これより遅くはならない」 |
| Ω(f(n)) | 下界（最良ケースの解析） | 「これより速くはならない」 |
| Θ(f(n)) | 上下が一致 | 「ちょうどこのオーダ」 |

> 補足: 試験では O 記法が圧倒的に頻出で、Ω 記法と Θ 記法は「定義を知っている」レベルで十分です。アルゴリズム比較の場面で出てくるのはほぼ O 記法だと思って構いません。

## 時間計算量と空間計算量

計算量には 2 つの観点があります。

- **時間計算量** （time complexity）: 実行に必要な「ステップ数（=時間）」のオーダ
- **空間計算量** （space complexity）: 実行に必要な「追加メモリ」のオーダ

たとえばマージソートは時間計算量 O(n log n) で速いものの、空間計算量 O(n) の作業領域が必要です。ヒープソートは時間計算量も O(n log n) で、さらに空間計算量 O(1) で済むため、メモリ制約が厳しい環境ではヒープソートのほうが好まれることがあります。

両者にはしばしばトレードオフがあります。動的計画法は「メモを保存する分の空間」を使って「時間を稼ぐ」典型例です。フィボナッチを素朴な再帰で書けば空間 O(n)（再帰スタック）・時間 O(2^n) ですが、DP なら空間 O(n)・時間 O(n) に改善できます。

## 代表的なオーダの比較

試験で必ず押さえたいオーダを、n=10 / 100 / 1,000 / 100 万 のときのステップ数で比較してみましょう。

| オーダ | 呼び方 | n=10 | n=100 | n=1,000 | n=100 万 |
|---|---|---|---|---|---|
| O(1) | 定数時間 | 1 | 1 | 1 | 1 |
| O(log n) | 対数時間 | 3 | 7 | 10 | 20 |
| O(n) | 線形時間 | 10 | 100 | 1,000 | 100 万 |
| O(n log n) | 線形対数時間 | 33 | 664 | 9,966 | 約 2,000 万 |
| O(n²) | 2 乗時間 | 100 | 10,000 | 100 万 | 10¹² (1 兆) |
| O(n³) | 3 乗時間 | 1,000 | 10⁶ | 10⁹ | 10¹⁸ |
| O(2^n) | 指数時間 | 1,024 | 10³⁰ | 天文学的 | 天文学的 |
| O(n!) | 階乗時間 | 約 360 万 | 10¹⁵⁷ | 天文学的 | 天文学的 |

n=100 万の行を見ると、各オーダの差が劇的に分かります。

- O(1) や O(log n) なら一瞬で終わる
- O(n) なら数秒
- O(n²) は 1 兆回の処理になり、現実的な時間では終わらない
- O(2^n) や O(n!) は宇宙が滅ぶまでに終わらない

**多項式時間** （polynomial time、O(n)、O(n²)、O(n³) など）と **指数時間** （exponential time、O(2^n)、O(n!) など）の境界はとても重要です。多項式時間なら現実的に扱えるサイズでも解ける一方、指数時間は n が少し増えるだけで実行不能になります。

## オーダの大小関係

代表的なオーダを小さい順（速い順）に並べると次のようになります。

```text
O(1) < O(log n) < O(n) < O(n log n) < O(n²) < O(n³) < O(2^n) < O(n!)
```

この順序は試験頻出です。「O(n log n) は O(n²) より速いが O(n) よりは遅い」という関係をいつでも答えられる状態にしておきましょう。

直感的なイメージとしては次の通りです。

- **O(1)** ： データ量に関係なく一定。ハッシュテーブルの平均アクセス、配列の添字アクセス
- **O(log n)** ： 倍々に減る範囲を絞る。二分探索、平衡二分探索木
- **O(n)** ： 全要素を 1 回ずつ見る。線形探索、配列のループ
- **O(n log n)** ： マージ・クイック・ヒープソートなどの比較ソート
- **O(n²)** ： 二重ループ。バブル・選択・挿入ソート
- **O(2^n)** ： 部分集合の全列挙、素朴なフィボナッチ
- **O(n!)** ： 順列の全列挙、巡回セールスマン問題の総当たり

## コードからオーダを見積もる方法

実際のコードからオーダを見積もる手順を確認します。

**ルール 1: ループは入れ子の数だけ次数が上がる**

```javascript
// 例: 単一ループは O(n)
for (let i = 0; i < n; i++) {
  console.log(arr[i]);
}
```

```javascript
// 例: 二重ループは O(n^2)
for (let i = 0; i < n; i++) {
  for (let j = 0; j < n; j++) {
    console.log(arr[i] + arr[j]);
  }
}
```

```javascript
// 例: 三重ループは O(n^3)
for (let i = 0; i < n; i++) {
  for (let j = 0; j < n; j++) {
    for (let k = 0; k < n; k++) {
      // ...
    }
  }
}
```

**ルール 2: ループ範囲が半分ずつ縮むなら O(log n)**

```javascript
// 例: 二分探索のループは O(log n)
let left = 0, right = n - 1;
while (left <= right) {
  const mid = Math.floor((left + right) / 2);
  // ... left = mid + 1 か right = mid - 1
}
```

**ルール 3: 連続する処理は最大のオーダを採用**

```javascript
// 例: 線形ループ O(n) + 二重ループ O(n^2) は全体で O(n^2)
for (let i = 0; i < n; i++) { ... }      // O(n)
for (let i = 0; i < n; i++) {            // O(n^2)
  for (let j = 0; j < n; j++) { ... }
}
// 全体: O(n) + O(n^2) = O(n^2)
```

**ルール 4: 再帰は呼び出し回数 × 1 回あたりの処理**

たとえばマージソートは「2 つに分けて再帰、結合に O(n)」なので、深さ log n 段 × 各段 O(n) = O(n log n) になります。

> よくある誤解: 「ループの内側で `array.indexOf()` を呼んでも O(n) でしょ」と思いがちですが、`indexOf` は内部で配列を線形探索するため O(n) です。それを n 回のループで呼ぶと全体で O(n²) になります。`Set` や `Map` のような O(1) アクセス可能なデータ構造に置き換えれば O(n) に落とせます。

## 多項式時間と指数時間：P と NP の入り口

計算量理論では、多項式時間で解けるかどうかでアルゴリズムを分類する枠組みがあります。

- **多項式時間アルゴリズム** : 計算量が `O(n^k)`（k は定数）。「現実的に解ける」とされる
- **指数時間アルゴリズム** : 計算量が `O(2^n)` や `O(n!)` 。n が小さくないと現実的に解けない

多項式時間で解けることが知られている問題のクラスを **P** 、解の正しさを多項式時間で検証できるが解くこと自体は未解明な問題のクラスを **NP** と呼びます。巡回セールスマン問題は NP の代表例で、試験では「NP 困難」「NP 完全」が単発で問われることがあります。

---

## 要点

- 計算量は **データ量 n に対する増え方** をオーダで表したもので、環境に依存しない普遍的な指標
- **O 記法** （ビッグオー）は上界、 **Ω 記法** は下界、 **Θ 記法** は上下が一致する場合
- 評価ルール: 定数項を無視、低次の項を無視、定数倍を無視、最高次のみを残す
- **時間計算量** と **空間計算量** は別軸で評価する。両者にトレードオフがあることが多い
- オーダの大小: **O(1) < O(log n) < O(n) < O(n log n) < O(n²) < O(2^n) < O(n!)**
- 二重ループは **O(n²)** 、範囲が半分になるループは **O(log n)** 、ソートを伴うなら **O(n log n)** が目安
- **多項式時間** （O(n^k)）と **指数時間** （O(2^n), O(n!)）の境界が「現実的に解ける」かどうかの分水嶺
