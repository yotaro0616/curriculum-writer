## あなたが書いた `php artisan serve` の裏で、何が起きているのか

Laravel の開発で `php artisan serve` を打つと、ローカルサーバが立ち上がり、ブラウザでアプリが動きます。同じように、JavaScript なら `node app.js`、C なら `gcc main.c -o main && ./main` で動かしてきたはずです。

これらのコマンドの裏側で行われている処理は、実は言語ごとにかなり違います。C はソースコードを **事前にすべて機械語に翻訳** してから実行ファイルを作るのに対し、PHP は **実行のたびに 1 行ずつ解釈** して動かしています。JavaScript の V8 エンジンに至っては、**頻繁に呼ばれる部分だけを動的に機械語化** するという、両者の中間的な戦略を取っています。

このセクションでは、ソースコードを動かすための仕組み、すなわち **言語処理系** （language processor）を体系的に見ていきます。実行が速い理由・遅い理由・デバッグしやすい理由が、処理系の仕組みから素直に説明できるようになります。

## コンパイラとインタプリタ

言語処理系の最も基本的な分類は、**コンパイラ** と **インタプリタ** の 2 つです。

### コンパイラ（compiler）

ソースコード全体をいったん機械語（または中間コード）に **翻訳** してから実行する方式です。翻訳結果は実行ファイル（`.exe` や ELF バイナリ）として保存され、以後は翻訳作業なしで何度でも実行できます。

代表的な言語: C、C++、Rust、Go、Swift

| 長所 | 短所 |
|---|---|
| 実行が高速（事前に最適化されている） | コンパイル時間がかかる |
| 配布時にソースコードを含めなくて良い | 1 か所修正するたびに再コンパイルが必要 |
| 型エラーなど多くの誤りを実行前に検出できる | 環境（OS・CPU）ごとに別の実行ファイルが必要 |

### インタプリタ（interpreter）

ソースコードを **1 行ずつ解釈しながら実行** する方式です。事前の翻訳作業がない代わりに、実行ごとに解釈の処理が走るため、純粋な実行速度はコンパイラに劣ります。

代表的な言語: Python、Ruby、伝統的な PHP、シェルスクリプト

| 長所 | 短所 |
|---|---|
| 修正してすぐ実行できる（コンパイル不要） | 実行が遅い |
| 対話的に試せる（REPL） | ソースコードを配布する必要がある |
| 環境差異を吸収しやすい | 型エラーなどが実行時まで分からない |

> 補足: PHP は伝統的にインタプリタですが、現代の PHP（PHP 7 以降）は内部でバイトコードに変換してから実行しており、OPcache などの仕組みで実質的に「実行ファイル」に近い動きをしています。「PHP はインタプリタ」というのは原理的な区分です。

### JIT コンパイラ（Just-In-Time compiler）

コンパイラとインタプリタのハイブリッドです。プログラムを実行しながら、**頻繁に実行される部分** （ホットスポット）を動的にコンパイルして機械語に変換し、以後はその機械語を使い回します。インタプリタの柔軟さとコンパイラの実行速度を両立する方式です。

代表的な処理系: JavaScript の V8 エンジン、Java の HotSpot VM、.NET の CLR

| 段階 | 動作 |
|---|---|
| 初回実行 | バイトコードをインタプリタで解釈実行 |
| 実行統計の収集 | どの関数が頻繁に呼ばれるかを記録 |
| ホットスポットの検出 | 一定回数以上呼ばれた箇所を特定 |
| JIT コンパイル | その箇所を機械語に変換、以後はキャッシュ |

ブラウザの JavaScript が「最初のクリックは少しもたつくが、操作を続けるうちに反応が良くなる」ように感じることがあるのは、JIT が裏で動いているためです。

## コンパイラの工程

コンパイラは内部で次の工程を順に実行します。試験で問われる定番の流れです。

```mermaid
flowchart LR
    A["ソースコード"] --> B["字句解析"]
    B --> C["構文解析"]
    C --> D["意味解析"]
    D --> E["中間コード生成"]
    E --> F["最適化"]
    F --> G["目的コード生成"]
    G --> H["目的プログラム"]
```

各工程の役割を 1 つずつ整理します。

### 字句解析（lexical analysis）

ソースコードを **トークン** （token、意味のある最小単位）の列に分解します。空白やコメントを除去し、`if`、`x`、`=`、`10`、`;` のような単位に切り出します。トークン化を担うのが **字句解析器** （lexer / scanner）です。

### 構文解析（syntactic analysis、パージング）

トークンの並びが文法的に正しいかを検証し、**抽象構文木** （AST、Abstract Syntax Tree）を構築します。BNF 記法で定義された文法（1-3-4 で扱った形式言語の文脈自由文法）に照らして木構造を組み立てます。担当するのが **構文解析器** （parser）です。

### 意味解析（semantic analysis）

構文的に正しいだけでなく、**意味的にも正しい** かを検証します。変数の型が合っているか、未宣言の変数を使っていないか、関数呼び出しの引数の数が合っているか、といったチェックを行います。

### 中間コード生成と最適化

機械語に直接変換する前に、**中間コード** （intermediate code）を生成します。中間コードは特定の CPU に依存しない抽象的な命令列で、最適化処理が施しやすい形になっています。最適化では、無駄な計算の削除（共通部分式の除去）、ループの簡略化、定数畳み込みなど、コードを賢く書き換える処理が行われます。

### 目的コード生成（code generation）

最適化された中間コードを、ターゲット環境の **機械語** （目的コード）に変換します。これで実行可能な状態に近づきます。

> よくある誤解: 「コンパイル = 機械語化」と単純に覚えがちですが、Java や C# のように **バイトコード** （仮想マシン用の中間表現）止まりで、機械語化は実行時の JIT に任せる言語も多くあります。試験では「Java のコンパイル結果は何か」と問われることがあり、答えは「バイトコード」です。

## リンカとローダ

コンパイラが生成するのは、多くの場合 **オブジェクトファイル** （`.o` や `.obj`）と呼ばれる、まだ不完全な中間生成物です。複数のソースファイルから作られたオブジェクトファイルや、外部ライブラリと結合して、初めて実行可能ファイルになります。

### リンカ（linker）

複数の **オブジェクトファイル** を結合し、外部ライブラリへの参照を解決して、1 つの実行ファイルを作るツールです。`main.c` と `helper.c` を別々にコンパイルしてできた `main.o` と `helper.o` を、`gcc main.o helper.o -o app` のように結合します。

リンクには 2 種類あります。

| 種類 | 結合タイミング | 特徴 | 例 |
|---|---|---|---|
| 静的リンク | コンパイル時 | ライブラリのコードが実行ファイル内に含まれる。実行ファイルが大きくなるが配布が簡単 | C の `-static` オプション |
| 動的リンク | 実行時 | 共有ライブラリを別ファイルとして残し、実行時に読み込む。複数プログラムで共有可能 | Windows の DLL、Linux の `.so` |

Linux で `apt install` した共有ライブラリ（`libssl.so` 等）が複数プログラムから使えるのは、動的リンクの仕組みのおかげです。

### ローダ（loader）

実行ファイルを **メモリ上に読み込み** 、実行を開始するための準備を行うプログラムです。OS の一部として動作し、ファイルからメモリへの転送、メモリアドレスの解決、共有ライブラリの紐づけなどを担当します。`./main` を実行したときに最初に動くのが（厳密にはシェルとカーネルを介して）ローダです。

### アセンブラ（assembler）

アセンブリ言語のソースコードを **機械語** に 1 対 1 で変換するツールです。`MOV AL, 61h` のようなニーモニックを 0 と 1 の並びに置き換えます。コンパイラの内部で目的コードを生成する段階の、より低レベル版と捉えると理解しやすいです。

### クロスコンパイラ（cross compiler）

実行環境とは **異なるアーキテクチャ** 向けの実行ファイルを作るコンパイラです。macOS 上で開発しながら iOS（ARM 系 CPU）向けのアプリをビルドする、Linux 開発機で組み込み機器（マイコン）向けのファームウェアを作る、といった場面で使われます。組み込み開発やモバイル開発で必須の概念です。

## バイトコードと仮想マシン

Java と .NET（C#）は、ソースコードを直接機械語にコンパイルせず、**バイトコード** という中間言語に変換します。バイトコードは **仮想マシン** （VM、Virtual Machine）の上で動作します。

| 言語 | バイトコード | 仮想マシン |
|---|---|---|
| Java | `.class` ファイル | JVM（Java Virtual Machine） |
| C# / F# | CIL（Common Intermediate Language） | CLR（Common Language Runtime） |

仮想マシンの最大の利点は **環境非依存性** です。同じ Java のバイトコードが、Windows でも macOS でも Linux でも、それぞれの JVM の上で動きます。「Write Once, Run Anywhere」のスローガンを支えているのがこの仕組みです。実行時は JVM が JIT コンパイラとして働き、ホットスポットを機械語化して高速化します。

## WebAssembly: Web の新しい実行基盤

現代の Web 開発で押さえておきたい話題として、**WebAssembly** （Wasm）があります。これは Web ブラウザ上で動作するバイナリ形式の中間言語で、C / C++ / Rust などのコンパイル結果を Wasm にし、ブラウザでネイティブに近い速度で実行できる仕組みです。試験必須ではありませんが、JavaScript と並んで動く新しい実行基盤として近年存在感を増しています。

## 要点

- **コンパイラ** （C、C++、Rust、Go）はソースコード全体を翻訳してから実行。実行が速いが修正に再コンパイルが必要
- **インタプリタ** （Python、Ruby、伝統的な PHP）は 1 行ずつ解釈実行。修正が即反映されるが実行は遅い
- **JIT コンパイラ** （V8、HotSpot、CLR）はインタプリタとコンパイラのハイブリッド。ホットスポットを動的に機械語化
- コンパイラの工程: **字句解析 → 構文解析 → 意味解析 → 中間コード生成 → 最適化 → 目的コード生成**
- **リンカ** は複数のオブジェクトファイルとライブラリを結合して実行ファイルを作る。**静的リンク** と **動的リンク** （DLL / `.so`）の 2 種類
- **ローダ** は実行ファイルをメモリに読み込み、実行を開始する
- **アセンブラ** はアセンブリ言語を機械語に変換、**クロスコンパイラ** は別アーキテクチャ向けの実行ファイルを作る
- Java の `.class` ファイルや .NET の CIL は **バイトコード** 。**JVM** や **CLR** という仮想マシン上で動作する
