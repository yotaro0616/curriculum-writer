## このセクションで学ぶこと

- 通信路や記憶装置でビットが化けてしまう「誤り」の発生メカニズム
- パリティチェックの仕組みと、検出できる誤り・できない誤りの境界
- CRC（巡回冗長検査）が大きなデータ塊に対して高い検出能力を持つ理由
- ハミング符号が誤りを「検出」するだけでなく「訂正」までできる仕組み

本セクションでは、情報を正確に届けるために付加する **冗長ビット** （redundant bit）の役割と、3 つの代表的な誤り検出 / 訂正方式を学びます。

---

## あなたのアプリが受け取ったデータは、本当に正しいのか

ブラウザがサーバから受け取ったレスポンスは、通信路の途中で 1 ビットも変化していないでしょうか。HDD に保存したファイルを 1 年後に読み出したとき、ビットが反転していないでしょうか。

実際の世界では、通信路のノイズ、ハードウェアの経年劣化、宇宙線（ソフトエラー）などの理由で、ビットが「0 から 1」「1 から 0」に化ける現象が一定の確率で起こります。Web アプリが何事もなく動いているように見えるのは、ハードウェアとプロトコルが裏側でこれらの誤りを検出・訂正してくれているからです。

TCP のパケットには `Checksum` フィールド、Ethernet フレームには `FCS`（Frame Check Sequence）、HDD / SSD には `ECC`（Error Correcting Code）、メモリの一部には ECC メモリ。受信側がメールの文字化けに気づけるのも、これらの仕組みのおかげです。本セクションでは、それらすべての基礎となる 3 つの方式を見ていきます。

---

## 誤り検出の基本：冗長ビットを足す

データ本体だけを送ると、ビットが化けても受信側はそれを知る術がありません。そこで、データに **冗長ビット** （余分なビット）を追加して送り、受信側で「データと冗長ビットが整合しているか」を検証します。冗長ビットがデータと矛盾していれば「誤りあり」と判断できます。

誤り検出技術には次の 3 段階があります。

| 種類 | 能力 | 代表例 |
|---|---|---|
| 誤り検出 | 誤りが起きたことを検出する | パリティ、CRC、チェックサム |
| 誤り訂正 | 検出して、さらに正しい値に直す | ハミング符号、ECC |
| 誤り再送 | 検出した後、送信側に再送を要求 | TCP の再送制御、ARQ |

冗長ビットを多く付けるほど検出 / 訂正能力は上がりますが、伝送量も増えます。用途に応じて適切な方式を選ぶことになります。

## パリティチェック：最もシンプルな誤り検出

**パリティチェック** （parity check）は、最も基本的な誤り検出方式です。データのビット列に「1 の個数を偶数（または奇数）にする 1 ビット」を付け加えるだけ。

**偶数パリティ** （even parity）の例。データ `1011010` に対して、1 の個数（4 個）が偶数になるよう、パリティビットは `0` を付加します。

```text
データ:        1 0 1 1 0 1 0  （1 が 4 個）
パリティビット:               0
送信ビット列:  1 0 1 1 0 1 0 0  （1 の総数が 4 個で偶数）
```

データ `1011011`（1 が 5 個、奇数）なら、偶数にするためにパリティビットは `1` を付加します。

```text
データ:        1 0 1 1 0 1 1  （1 が 5 個）
パリティビット:               1
送信ビット列:  1 0 1 1 0 1 1 1  （1 の総数が 6 個で偶数）
```

受信側は、受け取った 8 ビット全体で「1 の個数が偶数か」を確認します。奇数になっていれば、どこかで 1 ビットが化けたと判断できます。

**奇数パリティ** （odd parity）は逆で、1 の総数が奇数になるようパリティビットを設定します。

> よくある誤解: パリティチェックは「1 ビットの誤り」しか検出できません。同時に 2 ビットが反転すると、1 の総数の偶奇が元に戻ってしまうため、誤りが検出できないのです。また、誤りを「検出」できても「どのビットが化けたか」までは特定できないので「訂正」はできません。

**水平垂直パリティ** （二次元パリティ）は、データを格子状に並べて行方向と列方向の両方にパリティを付ける方式で、これなら 1 ビットの誤りについて行・列の交点として特定でき、訂正までできます。

## CRC：データ塊に強い検出方式

パリティが「1 ビット」単位の誤り検出なのに対し、**CRC** （Cyclic Redundancy Check、巡回冗長検査）は数十バイト〜数 KB の大きなデータ塊に対して、バースト誤り（連続するビット列がまとめて化ける誤り）まで高い確率で検出できます。Ethernet の FCS、ZIP ファイルの整合性チェック、HDD の内部処理など、現代の通信・記憶装置で広く使われています。

CRC の考え方は、データを長い 2 進数（多項式）と見なし、送受信者間で共有する **生成多項式** （generator polynomial）で割り算したときの「余り」を冗長ビットとして付ける、というものです。

```text
送信側: データ × 2^n を生成多項式で割り、余り R を求める
        送信ビット列 = データ + R

受信側: 受信ビット列を同じ生成多項式で割る
        余りが 0 なら誤りなし、0 でなければ誤りあり
```

この除算は通常の数の割り算ではなく、XOR を使った 2 進数の特殊な演算（mod 2 演算）で行います。XOR は 1-1-3 で学んだ「異なれば 1、同じなら 0」の論理演算でしたが、ここでは「桁ごとの引き算を借りなしで行う」ものとして使われます。

```text
1101 ÷ 1011 の例（XOR で行う）:
  1101
⊕ 1011
  ----
  0110  ← これが余り（厳密にはさらに桁を進めて計算）
```

実装上は、ハードウェアのシフトレジスタで非常に高速に計算できる点も CRC の利点です。Ethernet の CRC-32 は 32 ビットの冗長ビットで、典型的なパケットの誤り検出率がほぼ 100% に近いとされています。

> 補足: チェックサム（checksum）は CRC の親戚にあたる検出方式で、TCP / IP ヘッダの整合性確認などに使われています。仕組みはより単純で「データを一定長で区切って加算し、その下位 N ビットを冗長ビットにする」ものです。CRC ほどの検出能力はありませんが、計算が軽量なため上位プロトコルで好まれます。

## ハミング符号：1 ビット誤りを「訂正」する

パリティと CRC は「誤りを検出する」までで、訂正はできません。検出後は再送を要求するか、データを捨てるしかありません。これに対し **ハミング符号** （Hamming code）は、複数のパリティビットを巧妙に配置することで、1 ビット誤りなら「どの位置が化けたか」を特定して自動訂正できます。

仕組みのエッセンスは「複数のパリティを、それぞれデータの異なる組み合わせに対して付ける」というものです。受信側で各パリティの整合性を確認すると、その結果のパターンから「誤りの位置」が一意に特定できる、というのが核心です。

**ハミング符号（7, 4）** （データ 4 bit に対し冗長 3 bit を付加し計 7 bit で送る方式）の例で見てみます。データを `d₁ d₂ d₃ d₄`、パリティを `p₁ p₂ p₃` として、7 bit を次のように並べます。

```text
位置: 1   2   3   4   5   6   7
値:   p₁  p₂  d₁  p₃  d₂  d₃  d₄
```

各パリティが担当するビット位置（2 進数で各桁が 1 の位置）は次のとおりです。

```text
p₁（位置 1, 1=001）: 位置 1, 3, 5, 7 をカバー（最下位ビットが 1 のもの）
p₂（位置 2, 2=010）: 位置 2, 3, 6, 7 をカバー（中位ビットが 1 のもの）
p₃（位置 4, 4=100）: 位置 4, 5, 6, 7 をカバー（最上位ビットが 1 のもの）
```

各パリティは「自分が担当する位置の合計が偶数」になるよう値を決めます。受信側は同じパリティを 3 つ計算し、それぞれが合っていれば 0、ずれていれば 1 として 3 ビットの数字を作ります。この数字がそのまま「誤りが起きた位置の番号」になります。

```text
パリティ検査結果（p₃ p₂ p₁ の順に並べる）:
000 → 誤りなし
001 → 位置 1 が誤り
010 → 位置 2 が誤り
011 → 位置 3 が誤り
100 → 位置 4 が誤り
101 → 位置 5 が誤り
110 → 位置 6 が誤り
111 → 位置 7 が誤り
```

位置が特定できれば、そのビットを反転（0 と 1 を入れ替え）すれば訂正完了です。ハミング符号は **1 ビットの誤りを訂正、2 ビットの誤りを検出** できます（拡張ハミング符号ではさらに能力が上がります）。

> よくある誤解: ハミング符号は「2 ビット以上の誤りを訂正できる」と覚えがちですが、訂正できるのは **1 ビット** までです。2 ビット同時の誤りは検出のみ、3 ビット以上は誤った訂正をしてしまう可能性があります。HDD / SSD で使う実用的な ECC は、より強力な BCH 符号やリードソロモン符号で、複数ビットを訂正できる方式が採用されています。

## 3 方式の使い分け

| 方式 | 冗長ビット数 | 検出能力 | 訂正能力 | 主な用途 |
|---|---|---|---|---|
| 偶数 / 奇数パリティ | 1 bit | 1 ビット誤り | なし | RAM、シリアル通信 |
| CRC | 8〜32 bit | バースト誤りに強い | なし | Ethernet、ZIP、HDD セクタ |
| ハミング符号 | log₂(n)+1 bit 程度 | 2 ビット誤り検出 | 1 ビット訂正 | メモリ ECC、衛星通信 |

選ぶ基準は「再送できる環境か、できない環境か」です。Web の TCP 通信は再送が容易なので CRC で検出だけして、誤ったら再送します。一方、宇宙探査機からのデータや、リアルタイムで再送が間に合わないストリーミングでは、ハミング符号系の訂正能力を持つ符号が必要になります。メールが文字化けして届くのは、これらの仕組みをすり抜けた誤り、もしくは文字コードの解釈ミスが原因です。

---

## 要点

- 通信や記憶でビットが化ける誤りに対し、**冗長ビット** を付加して検出・訂正する
- **パリティチェック**: 1 ビット追加で 1 ビット誤りを検出（訂正不可）。2 ビット同時誤りは検出できない
- **偶数パリティ** は 1 の総数を偶数に、**奇数パリティ** は奇数にする
- **CRC** （巡回冗長検査）: 生成多項式で割った余りを冗長ビットにする。バースト誤りに強く、Ethernet・ZIP・HDD で広く使用
- **ハミング符号** : 複数のパリティで誤り位置を特定し、**1 ビット誤りを訂正、2 ビット誤りを検出**
- 使い分けは「再送できるか」で決まる。再送可能なら検出のみ（CRC）、不可能なら訂正能力（ハミング系）が必要
